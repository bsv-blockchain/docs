An overlay is a service that tracks the transactions of one app or protocol. Your app sends it the transactions it creates, the overlay keeps the outputs that follow your rules, and your app queries it later to read them back. It is how a BSV app keeps track of its own data, such as tokens, records or file references, without indexing every block on the chain. This page was written against `@bsv/sdk` 3.2.1.

## Why apps track their own transactions

A node keeps the whole chain, but it does not know which transactions belong to your app. An overlay starts from the other end: your app already has its transactions, because its wallet created them.

<OverlayCompare />

<Visibility for="agents">
The comparison has two columns. Index the chain yourself: you process every transaction on the network, you run the indexer or trust someone else's, you trust that the index left nothing out, and costs grow with the whole network. Use an overlay: you process only the transactions your app sends, the overlay checks each one, usually with SPV, it applies your own rules, and costs grow with your app.
</Visibility>

The state of a BSV app lives in <Hint tip="Unspent transaction output">UTXOs</Hint>, not in an account that a node updates. An output can be spent only once, and the miners reject a second spend. So when the overlay sees that an output it tracks was spent, it knows the state changed, and an app that holds an old copy finds out as soon as it tries to spend that output.

## The two parts of an overlay

An <Hint tip="Built from topic managers, which decide what is admitted, and lookup services, which query what was admitted.">overlay service</Hint> pairs a topic manager with a lookup service, and one overlay host can run many pairs. Their names start with `tm_` and `ls_`, as set by <Hint tip="BSV Request for Comments 87, the naming rules for topic managers and lookup services">BRC-87</Hint>:

<OverlayParts />

<Visibility for="agents">
The diagram shows one overlay host with two parts. The topic manager, named with the tm_ prefix, applies the rules of your protocol and admits only the outputs that pass, for example a token with a valid format. The admitted outputs go to the lookup service, named with the ls_ prefix, which indexes them and answers queries about them, for example all the tokens of one asset.
</Visibility>

## How a transaction goes through an overlay

A transaction goes through an overlay in five steps. The submission side is defined in <Hint tip="BSV Request for Comments 22, overlay network data synchronization">BRC-22</Hint> and the query side in <Hint tip="BSV Request for Comments 24, overlay network lookup services">BRC-24</Hint>.

<Steps>
  <Step title="Your app sends the transaction">
    Your app builds the transaction with its wallet and sends it to the overlay host in <Hint tip="Background Evaluation Extended Format (BRC-62)">BEEF</Hint>, with the names of the topics it is meant for.
  </Step>
  <Step title="The topic managers admit outputs">
    The host verifies the transaction, and each topic manager picks the outputs it admits.
  </Step>
  <Step title="The host answers with a STEAK">
    The <Hint tip="Submitted Transaction Execution AcKnowledgment">STEAK</Hint> lists the outputs each topic admitted.
  </Step>
  <Step title="The lookup service indexes them">
    The lookup service indexes the admitted outputs. When a later transaction spends one of them, the topic manager either removes it from the topic or keeps it as history.
  </Step>
  <Step title="Your app queries the lookup service">
    Your app queries the lookup service by name and gets back the matching outputs as BEEF, so it can verify them before it uses the data.
  </Step>
</Steps>

## How your app finds an overlay host

An overlay is shared infrastructure, and only a host that runs your topic can track it. Your app does not need the address of that host in advance: hosts announce what they run with two kinds of advertisement, defined in <Hint tip="BSV Request for Comments 88, overlay services synchronization architecture">BRC-88</Hint>:

- A <Hint tip="Services Host Interconnect Protocol">SHIP</Hint> advertisement says that a host runs a topic, so a transaction can be sent to every host that tracks it. In `@bsv/sdk`, `TopicBroadcaster` uses it to send a transaction to the hosts of its topics
- A <Hint tip="Services Lookup Availability Protocol">SLAP</Hint> advertisement says that a host runs a lookup service, so a query can find a host that answers it. In `@bsv/sdk`, `LookupResolver` uses it to send a query to a host of the service

Both classes find the hosts through SLAP trackers, the hosts that keep the list of advertisements for a network. Each network has its own trackers, so your app looks on the network where its host runs.

When no public host runs your topic, you run one. `@bsv/overlay-express` runs a host as a Node server, and `@bsv/overlay-topics` has ready topic managers and lookup services, for tokens, identity certificates, key-value storage and file references, among others.
