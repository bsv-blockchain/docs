---
title: "How overlays work"
description: "Overlays track the transactions of one app or protocol, so the app can look them up later without scanning the chain."
---

An overlay is a service that tracks the transactions of one app or protocol. Your app sends it the transactions it creates, the overlay keeps the outputs that follow your rules, and your app queries the overlay later to read them back. It is how a BSV app keeps track of its own data, such as tokens, records or file references, without indexing every block on the chain.

## Why apps track their own transactions

A node keeps the whole chain, but it does not know which transactions belong to your app. The usual way to find them is to listen to every transaction on the network and index the ones you need. At high transaction volumes that is expensive, and an app that reads from someone else's index has to trust that the index left nothing out.

An overlay works the other way. Your app already has its own transactions, because its wallet created them, so it sends them to the overlay directly. The overlay verifies each one, usually with <Hint tip="Simplified Payment Verification, which checks a transaction against block headers instead of the full chain">SPV</Hint>, and stores only what matches its rules, so neither your app nor the overlay processes the rest of the chain.

The state of a BSV app lives in <Hint tip="Unspent transaction output">UTXOs</Hint>, not in an account that a node updates. An output can be spent only once, and the miners reject a second spend. When the overlay sees that an output it tracks was spent, it knows the state changed. An app that holds an old copy of the state finds out as soon as it tries to spend an output that was already spent.

## How an overlay works

An <Hint tip="Built from topic managers, which decide what is admitted, and lookup services, which query what was admitted.">overlay service</Hint> has two parts:

- A topic manager decides which outputs of a transaction belong to a topic. It applies the rules of your protocol, for example that an output holds a token with a valid format, and admits only the outputs that pass.
- A lookup service indexes the admitted outputs and answers queries about them. The query format is up to the service, for example all the tokens of one asset.

A topic manager name starts with `tm_`, and a lookup service name starts with `ls_`, as set by <Hint tip="BSV Request for Comments 87, the naming rules for topic managers and lookup services">BRC-87</Hint>. One overlay host can run many pairs.

A transaction goes through an overlay in this order:

1. Your app builds the transaction with its wallet and sends it to the overlay host, in <Hint tip="Background Evaluation Extended Format (BRC-62)">BEEF</Hint>, with the names of the topics it is meant for.
2. The host verifies the transaction, and each topic manager picks the outputs it admits.
3. The host answers with a <Hint tip="Submitted Transaction Execution AcKnowledgment">STEAK</Hint>, the list of outputs each topic admitted.
4. The lookup service indexes the admitted outputs. When a later transaction spends one of them, the topic manager either removes it from the topic or keeps it as history.
5. Your app queries the lookup service by name and gets back the matching outputs as BEEF, so it can verify them before it uses the data.

The submission side is defined in BRC-22 and the query side in BRC-24.

## How your app finds an overlay host

An overlay is shared infrastructure, and only a host that runs your topic can track it. Your app does not need to know the address of that host in advance. Hosts announce what they run with two kinds of advertisement, defined in BRC-88:

- A <Hint tip="Services Host Interconnect Protocol">SHIP</Hint> advertisement says that a host runs a topic, so a transaction can be sent to every host that tracks it.
- A <Hint tip="Services Lookup Availability Protocol">SLAP</Hint> advertisement says that a host runs a lookup service, so a query can find a host that answers it.

In `@bsv/sdk`, `TopicBroadcaster` sends a transaction to the hosts of its topics, and `LookupResolver` sends a query to a host of the service. Both find the hosts through SLAP trackers, the hosts that keep the list of advertisements for a network. Each network has its own trackers, so the app has to look on the network where its host runs. This page was written against `@bsv/sdk` 3.2.1.

When no public host runs your topic, you run one. `@bsv/overlay-express` runs a host as a Node server, and `@bsv/overlay-topics` has ready topic managers and lookup services, for tokens, identity certificates, key-value storage and file references, among others.
