**BSV** apps are built from a small set of components. Your app asks for something to be done, a wallet decides whether and how, and a few services behind the wallet broadcast the transaction, check it against block headers and store what the app needs.

## How the pieces fit

<StackOverview />

Your app talks to the wallet through <Hint tip="The standard interface between app code and wallet code">BRC-100</Hint>. The app asks, the wallet decides, and the keys never leave the wallet. Because the interface is a standard, any BRC-100 wallet can take the place of another one without a change in your app. BSV Desktop runs on desktop and BSV Browser runs on mobile, and both are built on wallet toolbox, the package that handles wallet storage and signing.

There are no accounts on BSV. Every payment is an unspent output locked to a rule, usually a key, and a signature spends it and creates new outputs. A balance is the outputs the wallet can unlock.

## What sits behind the wallet

Each service below does one job:

- Broadcast service. The broadcast service, Arcade, takes a transaction and delivers it to block producing nodes, and your app or wallet can ask it for the status of a transaction.
- Block header service. It gives the wallet the block headers it checks proofs against. A block header is 80 bytes. Arcade serves headers too, and wallet toolbox includes a Chaintracks client for the same job.
- Message box. A store and forward channel for encrypted messages between people and apps, so the recipient does not have to be online when the message is sent.
- Overlays. An overlay indexes the transactions that matter to an app. A topic manager decides which outputs belong to a topic, and a lookup service answers queries about them.
- File storage. UHRP stores public files by their hash, so a file is found by what it is and not by where it lives.

## How an API charges for a request

HTTP 402 lets an API ask for payment in the request itself. The client asks for a resource, the server answers 402 with the price in the `x-bsv-sats` header, the wallet pays, and the same request goes again with the payment attached. The `@bsv/402-pay` package implements this flow, which is specified in BRC-121.

## Open standards

The interfaces between these parts are published as BRC standards, such as BRC-100 for the wallet and BRC-121 for 402 payments, so a wallet or a service can be built by anyone against the same specification. SDKs are available for TypeScript, Go, Python and Rust.


## Layers and packages

The packages of the TypeScript stack follow the same shape, as roles rather than as an npm dependency chain. There are three main layers, plus a set of capabilities that connect to them from the side.

The BRC-100 interface sits between the application and the wallet. Beside the layers are overlays (`@bsv/overlay`, `@bsv/overlay-express`), messaging (`@bsv/message-box-client`, `@bsv/authsocket`), identity (`@bsv/auth-express-middleware`), monetization (`@bsv/402-pay`, `@bsv/payment-express-middleware`) and tokens (`@bsv/btms`).

### The foundation, @bsv/sdk

`@bsv/sdk` sits at the bottom and has no runtime dependencies, so the part of the stack that handles your cryptography adds nothing to your `node_modules`. The other packages list it as a peer dependency and build on it. It covers:

- Cryptography: secp256k1 and secp256r1 ECDSA, Schnorr signatures, ECDH, plus SHA-256/512, RIPEMD-160 and HMAC.
- Script and transactions: a full Bitcoin Script interpreter, a transaction builder, serialization, the fee model and <Hint tip="Unspent transaction output, the unit a wallet spends">UTXO</Hint> handling.
- BEEF and Merkle proofs: the `Beef` class for <Hint tip="BRC-62, the format for sending a transaction with its proof">BEEF</Hint> encoding and decoding, and `MerklePath` for <Hint tip="BRC-74, the format of a Merkle proof">BUMP</Hint> proofs.
- Key derivation and network: BRC-42 and BRC-43 key derivation, `ARC` to submit transactions, and chain trackers such as `BlockHeadersService` to check proofs against block headers.

It also defines the BRC-100 types that the wallet layer and the wallet clients rely on.

### The wallet boundary, BRC-100

The BRC-100 wallet interface is the seam that separates app code from wallet code:

- Above the line, your app calls `createAction`, `signAction`, `listOutputs`, `listActions`, `internalizeAction` and other high-level methods. It never manages keys or storage.
- Below the line, the wallet handles storage, signing, key derivation, choosing which coins to spend and gathering Merkle proofs.

### Building a wallet, @bsv/wallet-toolbox

`@bsv/wallet-toolbox` is for developers who build a wallet rather than an app. It is a set of composable pieces:

| Module | Role |
| --- | --- |
| `WalletStorageManager` | Coordinates where wallet data is stored (active, backup and incremental sync) |
| `StorageKnex` | SQL storage (SQLite, MySQL, PostgreSQL) |
| `StorageIdb` | Storage inside the browser |
| `StorageClient` | Storage over HTTPS, for relay setups |
| `Monitor` | A background process that confirms transactions, fetches proofs and rebroadcasts anything stuck |
| `PrivilegedKeyManager` | Handles the higher permission keyring used for identity operations |
| `ShamirWalletManager` | Splits wallet backups with Shamir secret sharing |
| `WalletSigner` | Connects the BRC-100 `signAction` call to the SDK's signing logic |
| `Services` | Wires up the external services a wallet needs: Arcade for broadcasting, Chaintracks and WhatsOnChain |

Whatever you assemble from these pieces exposes the same BRC-100 interface that app packages such as `@bsv/simple` expect.

### Building an app, @bsv/simple

`@bsv/simple` is where most app developers start, because it spares you the BRC-100 calls. It has two entry points, and the one you need depends on who holds the keys:

- **`@bsv/simple/browser`:** for apps that use the user's own wallet. It wraps the SDK `WalletClient`, finds the BRC-100 wallet available on the user's machine (over localhost, `postMessage` or another supported channel) and your app never holds a private key. `wallet.getClient()` gives you the raw BRC-100 client.
- **`@bsv/simple/server`:** for a backend service or an automated agent that manages its own key, with a wallet storage endpoint behind it. It suits agents, backend services and MCP servers.

### Capabilities beside the stack

These packages do not stack on top of the three layers. They connect through BRC-100, through `@bsv/sdk` primitives or directly to a service API:

| Capability | Packages | What it gives you | Connects through |
| --- | --- | --- | --- |
| Data overlays | `@bsv/overlay`, `@bsv/overlay-express`, `@bsv/overlay-topics` | Shared, queryable on chain context: topic managers, lookup services, peer discovery | `@bsv/sdk` transactions, overlay services |
| Messaging and peer payments | `@bsv/message-box-client`, `@bsv/authsocket`, `@bsv/paymail` | Store and forward encrypted messages, live authenticated channels, payment address derivation (BRC-29) | BRC-100 wallet, BRC-103 and BRC-104 auth |
| Identity | `@bsv/auth-express-middleware`, `@bsv/authsocket` | An HTTP handshake and a peer identity framework (BRC-31) | BRC-100 wallet, BRC-103 and BRC-104 |
| Monetization | `@bsv/402-pay`, `@bsv/payment-express-middleware` | Pay per request APIs over HTTP 402, plus a separate legacy authenticated payment flow | BRC-100 wallet, BRC-121 for `402-pay` |
| Tokens | `@bsv/btms`, `@bsv/btms-permission-module` | Token metadata, wallet permission prompts and the PushDrop token pattern (BRC-48) | BRC-100 wallet, overlay topics |
| File storage | `@bsv/overlay-topics`, UHRP | Content addressed file storage and retrieval | UHRP servers, BRC-26 |

Your app can call overlays, message box servers and UHRP storage directly, without the wallet. The wallet is only involved when an operation needs a private key.
