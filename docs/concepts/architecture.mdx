BSV's developer stack has three main layers, plus a handful of capabilities that sit alongside them rather than stacking on top. If you've worked with another chain's SDK before, the shape should feel familiar: a low-level cryptography library at the bottom, a wallet boundary in the middle, and app-friendly packages on top.

## The Foundation: @bsv/sdk

`@bsv/sdk` sits at the bottom of everything and has zero external dependencies, which means no `node_modules` surface area in the part of the stack that handles your cryptography. Every other package builds on it. It covers:

<CardGroup cols={2}>
  <Card title="Cryptography" icon="key">
    secp256k1 and secp256r1 ECDSA, Schnorr signatures, ECDH, plus SHA-256/512, RIPEMD-160, and HMAC.
  </Card>
  <Card title="Script and transactions" icon="code">
    A full Bitcoin Script interpreter, a transaction builder, serialization, the fee model, and UTXO handling.
  </Card>
  <Card title="BEEF and Merkle proofs" icon="layer-group">
    The `Beef` class for <Hint tip="BRC-62, the format for sending a transaction with its proof">BEEF</Hint> encoding and decoding, and `MerklePath` for <Hint tip="BRC-74">BUMP</Hint> proofs.
  </Card>
  <Card title="Key derivation and network" icon="network-wired">
    BRC-42/43 key derivation, `ArcBroadcaster` to submit transactions, and `ChaintracksClient` for block headers.
  </Card>
</CardGroup>

It also defines the BRC-100 types that the wallet layer and wallet clients both rely on.

## The Wallet Boundary: BRC-100

The single most important seam in the stack is the <Hint tip="The standard interface between app code and wallet code">BRC-100 wallet interface</Hint>. Everything above it is app logic that never touches a key; everything below it is wallet logic that never needs to know what the app is actually building:

- **Above the line**: your app calls `createAction`, `signAction`, `listOutputs`, `listActions`, `internalizeAction`, and other high-level methods. It never manages keys or storage directly.
- **Below the line**: the wallet handles storage, signing, key derivation, choosing which coins to spend, and gathering Merkle proofs.

Because that boundary is standardized, you can swap in any BRC-100-compliant wallet underneath your app without changing a line of application code, the same idea behind WalletConnect on other chains.

## Building a Wallet: @bsv/wallet-toolbox

`@bsv/wallet-toolbox` is for the other side of that boundary, developers building a wallet rather than an app. It's not one monolithic wallet, it's a set of composable pieces you assemble:

| Module | Role |
| --- | --- |
| `WalletStorageManager` | Coordinates where wallet data is stored (active, backup, and incremental sync) |
| `KnexWalletStorage` | SQL-backed storage (SQLite, MySQL, PostgreSQL) |
| `IndexedDBWalletStorage` | Storage inside the browser |
| `RemoteWalletStorage` | Storage over HTTPS, for relay-style setups |
| `Monitor` | A background process that confirms transactions, fetches proofs, and rebroadcasts anything stuck |
| `PrivilegedKeyManager` | Handles the higher-permission keyring used for identity operations |
| `ShamirWalletManager` | Splits key backups using Shamir secret sharing |
| `WalletSigner` | Connects the BRC-100 `signAction` call to the SDK's actual signing logic |
| `Services` | Wires up the external services a wallet needs: ARC, Chaintracks, WhatsOnChain |

Whatever you assemble from these pieces ends up exposing the same BRC-100 interface that app-layer packages like `@bsv/simple` expect to talk to.

## Building an App: @bsv/simple

For most app developers, `@bsv/simple` is where to start, it's the layer built specifically to avoid making you deal with BRC-100 calls directly. It has two entry points, and which one you need depends on who holds the keys:

<CardGroup cols={2}>
  <Card title="@bsv/simple/browser" icon="globe">
    For apps that rely on the user's own wallet. It wraps the SDK's `WalletClient`, finds whatever BRC-100 wallet is available on the user's machine (over localhost, `postMessage`, or another supported channel), and your app never holds a private key. Need lower-level access? `wallet.getClient()` exposes the raw BRC-100 client underneath.
  </Card>
  <Card title="@bsv/simple/server" icon="server">
    For a backend service or automated agent that manages its own key, self-custodial, with a wallet storage endpoint behind it. Useful for things like automated agents, backend services, or an MCP server.
  </Card>
</CardGroup>

<Callout type="warning">
Our own testing found the `@bsv/simple/server` funding path blocked: the documented `fund-metanet` tool fails, and the funding transaction is rejected for an invalid AtomicBEEF on both storage servers we tested. Don't present this path as working end to end without flagging that.
</Callout>

## Capabilities That Sit Alongside the Stack

A few more packages don't fit neatly into the three layers above, instead they connect into the stack horizontally, through BRC-100, through `@bsv/sdk` primitives, or directly against a service's API:

| Capability | Packages | What it gives you | Connects through |
| --- | --- | --- | --- |
| Data overlays | `@bsv/overlay`, `@bsv/overlay-express`, `@bsv/overlay-topics` | Shared, queryable on-chain context: topic managers, lookup services, peer discovery | `@bsv/sdk` transactions, overlay services |
| Messaging and peer payments | `@bsv/message-box-client`, `@bsv/authsocket`, `@bsv/paymail` | Store-and-forward encrypted messages, live authenticated channels, payment address derivation (BRC-29) | BRC-100 wallet, BRC-103/104 auth |
| Identity | `@bsv/auth-express-middleware`, `@bsv/authsocket` | An HTTP handshake and peer identity framework (BRC-31) | BRC-100 wallet, BRC-103/104 |
| Monetization | `@bsv/402-pay`, `@bsv/payment-express-middleware` | Pay-per-request APIs over HTTP 402, plus a separate legacy authenticated payment flow | BRC-100 wallet; BRC-121 for `402-pay` |
| Tokens | `@bsv/btms`, `@bsv/btms-permission-module` | Token metadata, wallet permission prompts, and the PushDrop token pattern (BRC-48) | BRC-100 wallet, overlay topics |
| File storage | `@bsv/overlay-topics`, UHRP | Content-addressed file storage and retrieval | UHRP servers, BRC-26 |

## Talking to Services Directly

Your app doesn't have to go through the wallet for everything. Overlays, message box servers, and UHRP storage all expose their own APIs, and your app can call them directly. The wallet only needs to be involved when an operation actually requires a private key, everything else can talk to these services on its own. Private keys never leave the wallet; that boundary is what keeps key material separate from the rest of your application.
