A BRC-100 wallet is the program on the other side of every app request. Apps call methods such as `createAction` through <Hint tip="BSV Request for Comments 100, the standard interface between apps and wallets">BRC-100</Hint>, and the wallet carries them out. It holds the keys, chooses which coins fund each transaction, signs, stores the outputs it tracks and applies permissions before an app spends or uses a protected protocol. BSV Desktop and BSV Browser are two of these wallets, both built on the `@bsv/wallet-toolbox` packages, the TypeScript reference implementation. Build one when you are making a wallet product, a wallet-like service or a port of the wallet to another language. An app that only uses a wallet starts from the [SDKs overview](/docs/sdk/) instead.

## The path to a BRC-100 wallet

Each stage below builds on the one before it, from the interface your wallet answers to the servers it can run on.

### Learn the interface

Start with [BRC-100 Wallet Interface](/docs/concepts/wallet-model/). It lists the method groups, the two ways `createAction` can end (an immediate action, or a `signableTransaction` that the app finishes with `signAction`) and the difference between labels, tags and baskets. An app written against BRC-100 expects those exact results from your wallet, without knowing which wallet answers.

### Start from wallet-toolbox

`@bsv/wallet-toolbox` connects the `@bsv/sdk` primitives to the parts a wallet needs:

| Part | What it does |
| --- | --- |
| `Wallet` | Implements the BRC-100 methods |
| `WalletStorageManager` and storage providers | Keep the wallet's records in an active store, with optional backup stores |
| `WalletSigner` | Brings the wallet's keys into the SDK signing flow |
| Key managers | Derive keys with BRC-42 and BRC-43, manage privileged keys and run Shamir-based recovery |
| `Services` | Connect the wallet to broadcast, chain tracking and proof lookup |
| `Monitor` | Tracks confirmations, gathers Merkle proofs and rebroadcasts stalled transactions in the background |
| `WalletPermissionsManager` | Checks permissions around wallet methods |
| `MockChain` | Runs wallet tests without a live network |

The `Setup` class builds a wallet with its storage, services and monitor in one call, and the object it returns exposes each part so you can inspect or replace it. [Send a payment from a server](/docs/get-started/quick-start-server/) builds a wallet this way on testnet, with `Setup.createWalletSQLite`.

### Choose the platform and storage

The toolbox ships in three packages, one per platform, and each supports different storage:

| Package | Platform | Storage |
| --- | --- | --- |
| `@bsv/wallet-toolbox` | Node.js | SQLite, MySQL or another database that Knex supports |
| `@bsv/wallet-toolbox-client` | Browser | IndexedDB on the device, or remote |
| `@bsv/wallet-toolbox-mobile` | React Native | Remote |

Remote storage keeps the records on a Wallet Infra server that the wallet calls over HTTPS. The records hold the derivation data of each output, so recovering a wallet needs both the root key material and these records. A seed alone cannot rebuild every output.

### Add permissions

`WalletPermissionsManager` sits in front of the wallet and decides what each app may do. Every spending approval covers one operation and is never cached. Permission modules take over the protocols, baskets and labels reserved by BRC-98, BRC-99 and BRC-111, so a module can add its own rules for one kind of asset. For example, `@bsv/btms-permission-module` lets the spend prompt show a token's value, such as \$1.00 USD, instead of the 1 <Hint tip="The smallest unit of BSV. 100,000,000 satoshis make 1 BSV.">satoshi</Hint> that typically funds the token output.

### Test conformance

The ts-stack repository turns BRC-100 behavior into JSON test vectors, each with its inputs and the expected outputs, under `conformance/vectors/wallet/brc100/`. A wallet in any language reads the same files and compares its own results. Coverage is strongest for the deterministic crypto and key methods. Stateful cases carry an explicit classification instead of counting as passes, so a vector count alone does not prove a wallet passes every case.

The same vectors are how a port proves it matches the TypeScript reference. [go-wallet-toolbox](https://github.com/bsv-blockchain/go-wallet-toolbox) and [py-wallet-toolbox](https://github.com/bsv-blockchain/py-wallet-toolbox) bring the toolbox to Go and Python, and the [porting guide](https://github.com/bsv-blockchain/ts-stack/blob/main/conformance/PORTING_GUIDE.md) covers aligning another language.

### Run the backend services

Two ts-stack servers run only when the wallet needs them:

- Wallet Infra serves the toolbox storage over JSON-RPC, backed by MySQL, with mutual authentication and records scoped to each user. Wallets reach it with `StorageClient`. Run it to host remote storage for many wallet clients.
- The <Hint tip="Wallet Authentication Backend">WAB</Hint> verifies a user's phone number and stores the key shares that let the user sign in and recover the wallet on a new device. Run it when your wallet offers phone-based sign-in and recovery.
