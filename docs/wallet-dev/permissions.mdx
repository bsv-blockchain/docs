import BlueTable from '/snippets/BlueTable.jsx';

Register permission modules in your wallet so it can answer app requests that the standard permission checks cannot judge, such as spending a token or masking a card in a game. At the end, a test script sends four app requests through your wallet and shows which module answered each one. Add modules when your wallet must support token apps, the <Hint tip="Elliptic curve point multiplication">ECPM</Hint> key operation or a permission scheme of your own.

## Before you begin

You need Node.js 22 or newer and a wallet built with `@bsv/wallet-toolbox`. The example runs on testnet and creates a throwaway wallet, so no coins are needed. This page was written against `@bsv/wallet-toolbox` 2.15.1, `@bsv/btms-permission-module` 1.2.4 and `@bsv/ecpm-permission-module` 0.1.4.

## How it works

Every app request reaches your wallet through `WalletPermissionsManager`, a wrapper around the wallet. Each request carries its <Hint tip="The domain of the app that sent the request">originator</Hint>, and the manager checks the call against the name of the basket, protocol or label it uses:

- A standard name goes through the four built-in permissions: protocol, basket, certificate and spending. The manager raises a callback such as `onBasketAccessRequested`, your wallet shows its approval window, and a grant can be kept as a <Hint tip="A record of the grant that the wallet keeps on chain">permission token</Hint>. A spending authorization covers an amount, counted per calendar month, and the app spends against it until the amount is used up. Then the wallet asks again.
- A name that starts with `p ` followed by a scheme ID, such as `p btms` or `p ecpm`, goes to the module registered under that scheme ID. These names are reserved by <Hint tip="P Protocols">BRC-98</Hint>, <Hint tip="P Baskets">BRC-99</Hint> and <Hint tip="P Labels">BRC-111</Hint>, so an app cannot use them unless your wallet has a module for the scheme.
- A `p ` name with no module registered is rejected with an error.

A module receives the request in `onRequest`, decides whether to allow it, and can change the arguments. The wallet runs the call, then passes the result through the module's `onResponse`. Two modules are published on npm:

<BlueTable>

| Scheme ID | Package | What it handles | Approval callback |
| --- | --- | --- | --- |
| `btms` | `@bsv/btms-permission-module` | Listing, spending and burning tokens of the <Hint tip="Basic Token Management System">BTMS</Hint> in `p btms` baskets and labels | `promptHandler(originator, message)` |
| `ecpm` | `@bsv/ecpm-permission-module` | Elliptic curve point multiplication through `getPublicKey`, used by protocols such as mental poker (BRC-229) | `authorize(request)` |

</BlueTable>

Neither module draws a window. Each one calls a function you pass in, and your wallet shows the approval window there.

## Set up the project

The first step is to set up one Node.js project folder with the packages, a test wallet and a stand-in for the approval window:

<Steps>
  <Step title="Install the packages">
    Run this in the project folder:

    ```bash
    npm install @bsv/wallet-toolbox @bsv/btms-permission-module @bsv/ecpm-permission-module @bsv/btms @bsv/wallet-toolbox-client @bsv/sdk
    ```

    The two modules list `@bsv/btms`, `@bsv/wallet-toolbox-client` and `@bsv/sdk` as peer dependencies, so they are installed together.
  </Step>
  <Step title="Create a test wallet">
    <Callout type="warning">
      This file creates a random private key and throws it away when the script ends. Use it only on testnet, never send coins to it, and never paste a real key into a file like this one.
    </Callout>

    Create `wallet.mjs` in the project folder. It builds a testnet wallet that keeps its records in a local SQLite file:

    ```javascript wallet.mjs
    import { PrivateKey } from '@bsv/sdk'
    import { Setup } from '@bsv/wallet-toolbox'

    const rootKey = PrivateKey.fromRandom()
    const identityKey = rootKey.toPublicKey().toString()

    export const setup = await Setup.createWalletSQLite({
      env: {
        chain: 'test',
        identityKey,
        identityKey2: identityKey,
        filePath: undefined,
        taalApiKey: '',
        devKeys: { [identityKey]: rootKey.toHex() },
        mySQLConnection: ''
      },
      filePath: './test-wallet.sqlite',
      databaseName: 'testwallet'
    })
    ```

    - `chain: 'test'` puts the wallet on testnet.
    - `setup.wallet` is the wallet the modules wrap, and `setup.keyDeriver` derives its keys. If your wallet is built another way, use your own `Wallet` instance and its key deriver in the next steps.
  </Step>
  <Step title="Add the approval window">
    Write `prompt.mjs`, a stand-in for the approval window of your wallet that prints the request and approves it:

    ```javascript prompt.mjs
    export async function askUser (originator, request) {
      console.log(`Approval window: ${originator} asks for`, request)
      return true
    }
    ```

    In your wallet, replace the body with your own window. Show the originator, show every value as plain text, and return `true` only when the user clicks to approve. Closing the window, a timeout or a rendering error returns `false`.
  </Step>
</Steps>

## Register the modules

Each module goes in a new file, `permissions.mjs`, which exports the wrapped wallet your app requests go through:

<Steps>
  <Step title="Create the BTMS module">
    Start `permissions.mjs` with the imports and the BTMS module:

    ```javascript permissions.mjs
    import { WalletPermissionsManager } from '@bsv/wallet-toolbox'
    import { createBtmsModule } from '@bsv/btms-permission-module'
    import { createEcpmModule } from '@bsv/ecpm-permission-module'
    import { setup } from './wallet.mjs'
    import { askUser } from './prompt.mjs'

    const btms = createBtmsModule({
      wallet: setup.wallet,
      promptHandler: async (originator, message) => {
        const request = message.startsWith('{') ? JSON.parse(message) : { message }
        return await askUser(originator, request)
      }
    })
    ```

    - `message` is a JSON string with a `type` of `btms_access`, `btms_spend` or `btms_burn`, plus the token details, or plain text when the module cannot read the token safely. The `startsWith('{')` check covers both.
    - Without `promptHandler`, the module denies every request.
    - An approval lasts 60 seconds per originator, and a spend approval covers only the exact transaction the user saw.
  </Step>
  <Step title="Create the ECPM module">
    Add the ECPM module under the BTMS one:

    ```javascript permissions.mjs
    const ecpm = createEcpmModule({
      keyDeriver: setup.keyDeriver,
      authorize: async request => {
        return await askUser(request.originator, {
          operation: request.operation,
          protocol: request.logicalProtocolID,
          counterparty: request.counterparty
        })
      }
    })
    ```

    - `request.operation` is `apply` or `remove`, and `request.logicalProtocolID` is the protocol name the app gave after the point.
    - Security level 0 requests run without calling `authorize`. Levels 1 and 2 call it, and level 2 approvals apply to one counterparty only.
    - To support <Hint tip="Requests that use the privileged keys of the wallet, kept apart from its everyday keys">privileged requests</Hint>, also pass `privilegedKeyDeriver`, a function that receives the reason and returns the privileged key deriver once the user approves.
  </Step>
  <Step title="Write a module of your own">
    <Callout type="warning">
      A request routed to a module skips the standard permission checks and tokens. Your module alone decides, so throw an error to deny, and never let the request through by default.
    </Callout>

    Below the ECPM module, write a module for a scheme of your own, `receipts`, that asks the user once per app before it may use a `p receipts` basket:

    ```javascript permissions.mjs
    const approved = new Set()
    const receipts = {
      async onRequest ({ method, args, originator }) {
        if (!approved.has(originator)) {
          const ok = await askUser(originator, { method, basket: args.basket })
          if (ok !== true) throw new Error('The user denied access to receipts.')
          approved.add(originator)
        }
        return { args }
      },
      async onResponse (result) {
        return result
      }
    }
    ```

    - `onRequest` returns `{ args }`, the arguments the wallet runs the call with. Return them unchanged or adjusted.
    - `onResponse` receives the wallet's result and returns what the app gets.
    - The `approved` set keeps approvals in memory only, so they end when the wallet stops.
    - A module can also define `handleRequest` to answer the call itself instead of passing it to the wallet. The ECPM module does this for `getPublicKey`.
  </Step>
  <Step title="Register the modules in the manager">
    Close `permissions.mjs` with the manager and a function that releases the modules:

    ```javascript permissions.mjs
    export const wallet = new WalletPermissionsManager(setup.wallet, 'admin.wallet.local', {
      permissionModules: { btms, ecpm, receipts }
    })

    export async function closeWallet () {
      btms.dispose()
      ecpm.dispose()
      approved.clear()
      await setup.activeStorage.destroy()
    }
    ```

    - Each key of `permissionModules` is the scheme ID the module answers for.
    - `'admin.wallet.local'` is the admin originator, the name your wallet uses for its own calls. The standard checks always allow it, so never give an app this name.
    - `dispose()` clears the approvals the two published modules hold in memory. Call it when the user logs out or the wallet shuts down.
  </Step>
</Steps>

## Check the modules

With the modules registered, send app requests through the wrapped wallet and see which one answers:

<Steps>
  <Step title="Write the check script">
    Create `check.mjs`. It makes four requests as the app `app.example.com`, one per scheme plus one with no module:

    ```javascript check.mjs
    import { PrivateKey } from '@bsv/sdk'
    import { wallet, closeWallet } from './permissions.mjs'

    const app = 'app.example.com'

    async function check (name, call) {
      try {
        console.log(`${name}: allowed`, await call())
      } catch (error) {
        console.log(`${name}: rejected, ${error.message}`)
      }
    }

    await check('receipts', () =>
      wallet.listOutputs({ basket: 'p receipts coffee' }, app))

    await check('btms', () =>
      wallet.listOutputs({ basket: 'p btms ASSET_ID' }, app))

    const point = PrivateKey.fromRandom().toPublicKey().toString()
    await check('ecpm', () =>
      wallet.getPublicKey({
        protocolID: [2, `p ecpm apply ${point} mental poker deal`],
        keyID: 'deck mask',
        counterparty: 'self'
      }, app))

    await check('loyalty', () =>
      wallet.listOutputs({ basket: 'p loyalty points' }, app))

    await closeWallet()
    ```

    - The second argument of each call is the originator, the app the request comes from. In a real wallet it comes from the connection to the app.
    - `ASSET_ID` stands for a BTMS asset ID. Replace it with one your wallet holds, or keep it to see the approval flow on an empty basket.
    - The ECPM request passes a random point, as a card game passes a card. The protocol ID holds the operation, the point and the protocol name.
  </Step>
  <Step title="Run the check">
    Run the script:

    ```bash
    node check.mjs
    ```

    The output shows each approval window, then the answer the app gets:

    ```text
    Approval window: app.example.com asks for { method: 'listOutputs', basket: 'p receipts coffee' }
    receipts: allowed { totalOutputs: 0, outputs: [] }
    Approval window: app.example.com asks for {
      type: 'btms_access',
      action: 'access BTMS tokens',
      assetId: 'ASSET_ID'
    }
    btms: allowed { totalOutputs: 0, outputs: [] }
    Approval window: app.example.com asks for {
      operation: 'apply',
      protocol: 'mental poker deal',
      counterparty: 'self'
    }
    ecpm: allowed {
      publicKey: '0261b9508a916747fcddc6b77e23c359fb6cbb09baf71b9ee53248a77a9d1d22f7'
    }
    loyalty: rejected, Unsupported P-module scheme: p loyalty
    ```

    - The test wallet is new, so the `receipts` and `btms` lists are empty.
    - `ecpm` returns the point multiplied by a key the wallet derives. The app gets the new point, never the key. The value changes on every run because the point is random.
    - `loyalty` is rejected because no module is registered for that scheme.
  </Step>
</Steps>

Your wallet now answers `p btms`, `p ecpm` and `p receipts` requests through its modules, and rejects any other `p ` scheme. When `askUser` returns `false`, the same script prints `rejected` for every request, with the error each module throws.
