Start a <Hint tip="BSV Request for Comments 100, the standard interface between apps and wallets">BRC-100</Hint> wallet on `@bsv/wallet-toolbox` with its `Setup` helpers, then decide where the wallet keeps its records. At the end, you have a testnet wallet in Node.js with SQLite storage, a running Monitor and a backup copy of its records, plus the call that opens the same wallet on remote storage or in a browser. Start here when you build a wallet product or a wallet-like service. The `Setup` helpers build the whole wallet in one call and return each part, so you can start from a working wallet and replace one part at a time.

## Before you begin

You need Node.js 22 or newer. The example runs on testnet with a new wallet that holds no coins, so it needs no funding. This page was written against `@bsv/wallet-toolbox` 2.15.1 and `@bsv/wallet-toolbox-client` 2.15.1, with `@bsv/sdk` 4.0.1.

## How it works

The `Setup` class turns two keys in a `.env` file into a complete wallet:

<ToolboxSetupFlow />

<Visibility for="agents">
How Setup builds a wallet, in four steps: .env holds two testnet keys written once by Setup.makeEnv(). Setup.getEnv('test') reads the keys and sets the chain to testnet. Setup.createWalletSQLite builds the key deriver, the storage, the services and the Monitor, then the wallet. setup is the object your code uses: the wallet and every part behind it.
</Visibility>

The `setup` object it returns gives you each part by name:

<BlueTable>

| Field | What you use it for |
| --- | --- |
| `wallet` | The BRC-100 wallet. Your code and the apps call its methods, such as `createAction` and `listOutputs` |
| `storage` | The `WalletStorageManager`, which holds the active store and its backups and can switch between them |
| `activeStorage` | The `StorageKnex` provider that writes to the SQLite file |
| `services` | The `Services` the wallet uses on testnet to broadcast, track the chain and look up proofs |
| `monitor` | The `Monitor`. `Setup` creates it but does not start it |
| `identityKey`, `keyDeriver`, `rootKey` | The keys from `.env`. `identityKey` is the public key that apps see |
| `chain`, `userId` | `test` for testnet, and the ID of the wallet's user record in the store |

</BlueTable>

## Create a testnet wallet

The first step is to create a Node.js project folder with the toolbox, the keys and a wallet that opens on SQLite:

<Steps>
  <Step title="Install the toolbox">
    Create an empty folder, open it in the terminal and install `@bsv/wallet-toolbox`:

    ```bash
    npm init -y
    npm install @bsv/wallet-toolbox
    ```

    The toolbox installs `@bsv/sdk`, Knex and SQLite with it, so the wallet needs no database server.
  </Step>
  <Step title="Keep the keys out of git">
    Create `.gitignore` in the project folder, so the keys and the wallet files never reach a repository:

    ```text .gitignore
    .env
    *.sqlite
    node_modules
    ```
  </Step>
  <Step title="Generate the keys">
    <Callout type="warning">
      The `.env` file holds the private keys of the wallet. Keep it private, never print it, paste it into code or commit it, and use this wallet only on testnet. Anyone with this file can spend the coins of the wallet.
    </Callout>

    Write the keys to `.env` with `Setup.makeEnv()`. Save this script as `create-env.mjs` in the same folder:

    ```javascript create-env.mjs
    import { existsSync, writeFileSync } from 'node:fs'
    import { Setup } from '@bsv/wallet-toolbox'

    if (existsSync('.env')) {
      console.log('.env already exists, nothing was written.')
    } else {
      writeFileSync('.env', Setup.makeEnv(), { mode: 0o600 })
      console.log('Wrote the test wallet keys to .env.')
    }
    ```

    Run it once:

    ```bash
    node create-env.mjs
    ```

    ```text
    Wrote the test wallet keys to .env.
    ```

    The script never prints the keys, and it does not replace an existing `.env`.
  </Step>
  <Step title="Open the wallet">
    Create `wallet.mjs`, a module that the other scripts import to open the wallet:

    ```javascript wallet.mjs
    import { Setup } from '@bsv/wallet-toolbox'

    process.loadEnvFile('.env')
    const env = Setup.getEnv('test')

    export const setup = await Setup.createWalletSQLite({
      env,
      filePath: './wallet.sqlite',
      databaseName: 'mywallet'
    })
    ```

    - `Setup.getEnv('test')` reads the keys and puts the wallet on testnet. `test` is the name the toolbox uses for testnet.
    - `Setup.createWalletSQLite` creates `wallet.sqlite` on the first run and sets up its tables. `databaseName` becomes the name of this store.
  </Step>
  <Step title="Check the wallet">
    Write `check.mjs`, which asks the wallet for its identity key, its network and its outputs:

    ```javascript check.mjs
    import { setup } from './wallet.mjs'

    const { wallet } = setup

    const { publicKey } = await wallet.getPublicKey({ identityKey: true })
    console.log('Identity key:', publicKey)

    const { network } = await wallet.getNetwork({})
    console.log('Network:', network)

    const outputs = await wallet.listOutputs({ basket: 'default' })
    console.log('Outputs:', outputs)

    await wallet.destroy()
    ```

    Run it:

    ```bash
    node check.mjs
    ```

    ```text
    Identity key: 023d8dae4bcebdf3267ecc700c26f800ee8182b268fd230dd2b9a223676d591b10
    Network: testnet
    Outputs: { totalOutputs: 0, outputs: [] }
    ```

    - The identity key is different for every `.env`.
    - `default` is the <Hint tip="A named group of outputs the wallet tracks">basket</Hint> that holds the coins the wallet spends from. It is empty because the wallet is new.
    - `destroy()` closes the storage, so the script can end.
  </Step>
</Steps>

The wallet now answers BRC-100 calls on testnet and keeps its records in `wallet.sqlite`. [Fund the server wallet from BSV Desktop](/get-started/quick-start-server/#fund-the-server-wallet-from-bsv-desktop) gives the same kind of wallet its first coins.

## Start the Monitor

With the wallet open, start its <Hint tip="The toolbox component that broadcasts queued transactions, gathers proofs and repairs wallet state in the background">Monitor</Hint>, which finishes the work that wallet methods leave for later, such as delayed broadcasts and <Hint tip="The proof that a transaction is in a block, checked against the block header">Merkle proofs</Hint>. A script that ends right away does not need it, and a wallet that runs as a service does:

<Steps>
  <Step title="Write the service script">
    Create `monitor.mjs`, which starts the Monitor and stops it cleanly on Ctrl+C:

    ```javascript monitor.mjs
    import { setup } from './wallet.mjs'

    const { wallet, monitor } = setup

    const running = monitor.startTasks()
    console.log('Monitor running. Press Ctrl+C to stop.')

    process.once('SIGINT', async () => {
      monitor.stopTasks()
      await running
      await wallet.destroy()
      console.log('Monitor stopped.')
    })
    ```

    - `startTasks()` runs the Monitor tasks on an interval until `stopTasks()` is called.
    - Stop the Monitor before `destroy()`, so no task writes to a closed store.
  </Step>
  <Step title="Run the service">
    Start it, and press Ctrl+C when you want it to stop:

    ```bash
    node monitor.mjs
    ```

    ```text
    Monitor running. Press Ctrl+C to stop.
    Monitor stopped.
    ```
  </Step>
</Steps>

In your wallet service, start the Monitor once, next to the code that answers app requests. [How the toolbox tracks UTXOs](/wallet-dev/wallet-toolbox/utxo-lifecycle/#what-the-monitor-settles-in-the-background) lists what each Monitor task does.

## Add a backup store

The storage manager can keep backup stores next to the active one and copy the records to them. A wallet needs these records to recover its outputs, since the keys in `.env` alone cannot rebuild them. Follow these steps to add a second SQLite file as a backup:

<Steps>
  <Step title="Write the backup script">
    Create `backup.mjs` in the project folder. It opens a second store, adds it to the storage manager and copies the records:

    ```javascript backup.mjs
    import { Setup } from '@bsv/wallet-toolbox'
    import { setup } from './wallet.mjs'

    const { storage, wallet } = setup
    const active = storage.getActiveStore()

    const backup = await Setup.createStorageKnex({
      env: Setup.getEnv('test'),
      knex: Setup.createSQLiteKnex('./backup.sqlite'),
      databaseName: 'mywallet-backup'
    })
    await storage.addWalletStorageProvider(backup)
    await storage.setActive(active)
    await storage.updateBackups()

    for (const store of storage.getStores()) {
      console.log(`${store.storageName}: ${store.isActive ? 'active' : 'backup'}`)
    }

    await wallet.destroy()
    ```

    - `getActiveStore()` returns the key of the active store, `wallet.sqlite`.
    - A new store marks itself as active when it is added. `setActive(active)` keeps `wallet.sqlite` as the active store and turns the new one into its backup.
    - `updateBackups()` copies the records from the active store to every backup.
  </Step>
  <Step title="Run the backup">
    Run the script:

    ```bash
    node backup.mjs
    ```

    ```text
    mywallet: active
    mywallet-backup: backup
    ```

    `backup.sqlite` now holds a copy of the wallet records. Run the script again to copy later changes.
  </Step>
</Steps>

The backup holds the same records as the active store, so protect it the same way. To switch stores, pass the key of a backup store to `setActive`, and that store becomes the active one.

## Choose the storage

Each `Setup` call opens the same wallet on a different store. Pick the store by where the wallet runs:

<CardGroup cols={3}>
  <Card title="SQLite or MySQL" icon="database">
    A wallet in Node.js, such as a server wallet or a desktop app. The records stay in a database you run, through Knex.
  </Card>
  <Card title="Remote storage" icon="cloud">
    A wallet that keeps its records on a storage server and reaches it over HTTPS with `StorageClient`.
  </Card>
  <Card title="IndexedDB" icon="app-window">
    A wallet that runs in a browser and keeps its records on the user's device.
  </Card>
</CardGroup>

The tabs below show the call for each one:

<Tabs>
<Tab title="SQLite or MySQL">

`wallet.mjs` above already uses SQLite:

```javascript
const setup = await Setup.createWalletSQLite({ env, filePath: './wallet.sqlite', databaseName: 'mywallet' })
```

For MySQL, call `Setup.createWalletMySQL({ env, databaseName })` instead. It reads the connection from `MYSQL_CONNECTION` in `.env`, a JSON string with the host, port, user and password, and the schema named by `databaseName` must already exist. Both calls go through `Setup.createWalletKnex`, which accepts any Knex instance in its `knex` argument.

</Tab>
<Tab title="Remote storage">

Save this as `remote-wallet.mjs` in the same project to open the wallet on a storage server:

```javascript remote-wallet.mjs
import { Setup } from '@bsv/wallet-toolbox'

process.loadEnvFile('.env')
const env = Setup.getEnv('test')

const setup = await Setup.createWalletClient({
  env,
  endpointUrl: 'https://go-wallet-testnet-us-1.bsvblockchain.tech'
})

for (const store of setup.storage.getStores()) {
  console.log(store.storageClass, store.endpointURL)
}

await setup.wallet.destroy()
```

```text
StorageClient https://go-wallet-testnet-us-1.bsvblockchain.tech
```

- `endpointUrl` is the storage server. It must run on the same network as the wallet, and this one runs on testnet.
- The records live on the server, and the keys stay in `.env` on your machine.

</Tab>
<Tab title="IndexedDB">

Install the browser package in your web app:

```bash
npm install @bsv/wallet-toolbox-client
```

Then open the wallet with `SetupClient.createWalletIdb`:

```javascript wallet.js
import { SetupClient } from '@bsv/wallet-toolbox-client'

export async function openWallet (rootKeyHex) {
  return await SetupClient.createWalletIdb({
    chain: 'test',
    rootKeyHex,
    databaseName: 'mywallet'
  })
}
```

- A browser has no `.env`, so `rootKeyHex` comes from the key management of your wallet, such as a key the user unlocks. Never ship a key in the app bundle.
- `databaseName` names the IndexedDB database on the device.

</Tab>
</Tabs>

<Visibility for="agents">
The three storage choices: SQLite or MySQL through Knex for a wallet in Node.js (Setup.createWalletSQLite, Setup.createWalletMySQL, Setup.createWalletKnex); remote storage on a storage server reached over HTTPS with StorageClient (Setup.createWalletClient with endpointUrl); IndexedDB in the browser (SetupClient.createWalletIdb from @bsv/wallet-toolbox-client, with chain, rootKeyHex and databaseName).
</Visibility>

Whichever store you pick, the wallet methods and the `setup` fields stay the same.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Backup store is not accepted">
    `updateBackups()` throws `WERR_NOT_ACTIVE: WalletStorageManager is not accessing user's active storage or there are conflicting active stores configured.` A new store marks itself as active when it is added, so the manager sees two active stores. Call `storage.setActive()` with the key of the store you want as active, as in `backup.mjs`, before `updateBackups()`.
  </Accordion>
  <Accordion title="New wallet cannot send a payment">
    `createAction` throws `WERR_INSUFFICIENT_FUNDS` with the number of <Hint tip="The smallest unit of BSV. 100,000,000 satoshis make 1 BSV.">satoshis</Hint> that are needed. A new wallet holds no coins. Fund it first, for example with [Fund the server wallet from BSV Desktop](/get-started/quick-start-server/#fund-the-server-wallet-from-bsv-desktop).
  </Accordion>
</AccordionGroup>
