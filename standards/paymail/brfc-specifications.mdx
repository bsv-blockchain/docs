Look up how a Paymail extension is specified and identified. Each extension is described in a <Hint tip="Bitcoin SV Request for Comments, a specification document identified without a central numbering authority">BRFC</Hint> document, and the BRFC ID of that document is the key a Paymail host uses to advertise the extension. To read a host's capabilities, match the published IDs listed below. Compute an ID only when you publish a BRFC of your own.

## What a BRFC document is

A BRFC is a specification that anyone can publish. No central authority assigns numbers or approves a proposal, and an implementer supports a BRFC by implementing it and advertising it during [capability discovery](/standards/paymail/capability-discovery/). The document has no fixed format or location. The [Specification Documents](https://github.com/bitcoin-sv-specs/brfc-paymail/blob/2e03c8bc49b489d13eda7a3580795b1809cd2f08/src/01-01-specification-documents.md) section of the 2019 specification recommends that it carry this metadata, as YAML front matter when the document is a Markdown file:

<BlueTable>

| Field | Required | Value |
| --- | --- | --- |
| `title` | Yes | The proposal title |
| `author` | No | Free form, such as a name, an alias, a Paymail address or a social media handle |
| `version` | No | No set format, such as a sequence number or a publication date |
| `supersedes` | No | The BRFC ID, or list of IDs, that this document replaces |

</BlueTable>

The specification advises against semantic versioning, because a host either supports a specification or it does not. To add a feature, publish a new extension specification, or update the specification and list the old BRFC ID in `supersedes`.

## How a BRFC ID is computed

To find the ID of an existing BRFC, use the ID its document publishes instead of computing it again. Some IDs in the 2019 documents were computed from fewer fields than their metadata lists. For example, `0c4339ef99c2` (Public Key Infrastructure) is the hash of the title alone. The BRFC ID Assignment test case for PayTo, `74524c4d6274`, is also not the key hosts use, which is `7bd25e5a1fc6`.

The BRFC ID is a hash of the metadata, so it changes when the title, the author or the version changes. The [BRFC ID Assignment](https://github.com/bitcoin-sv-specs/brfc-paymail/blob/2e03c8bc49b489d13eda7a3580795b1809cd2f08/src/01-02-brfc-id-assignment.md) section of the 2019 specification defines these steps:

1. Take the `title`, `author` and `version` values, and leave out any that are absent.
2. Trim the whitespace at the start and end of each value, and keep the whitespace inside it.
3. Concatenate the values and encode the string as UTF-8 bytes.
4. Hash the bytes with double SHA-256.
5. Reverse the bytes of the hash, as Bitcoin does to display a hash, and hex-encode them.
6. Keep the first 12 hexadecimal characters, which are the last six bytes of the raw hash in reverse order.

This Node.js script runs the same steps with the built-in `crypto` module, on the metadata of the BRFC Specifications document:

```javascript brfc-id.mjs
import { createHash } from 'node:crypto'

const sha256 = (bytes) => createHash('sha256').update(bytes).digest()

function brfcId ({ title, author = '', version = '' }) {
  const input = title.trim() + author.trim() + version.trim()
  const hash = sha256(sha256(Buffer.from(input, 'utf8')))
  return Buffer.from(hash).reverse().toString('hex').substring(0, 12)
}

console.log(brfcId({ title: 'BRFC Specifications', author: 'andy (nChain)', version: '1' }))
```

Run it with `node brfc-id.mjs`. It prints the ID that the specification gives for this document:

```text
57dd1f54fc67
```

Pass each value as a string. A YAML parser reads `version: 1` as a number.

## Where the BRFC ID appears

A Paymail host lists the extensions it supports in the `capabilities` object of its `/.well-known/bsvalias` document. Each key is a BRFC ID, and the BRFC with that ID defines the value. The Paymail standard gives this example for Payee Approvals, with BRFC ID `3d7c2ca83a46`:

```json
{
  "bsvalias": "1.0",
  "capabilities": {
    "3d7c2ca83a46": {
      "callback": "https://example.org/{alias}@{domain.tld}/payment-destination-response"
    }
  }
}
```

A client replaces `{alias}` and `{domain.tld}` with the parts of the Paymail handle before it sends a request. The full document, and how a client finds it, are in [Discover Paymail capabilities](/standards/paymail/capability-discovery/) and in the [Capability Discovery](https://tsc.bsvblockchain.org/standards/paymail/#PaymailStandardDocument-CapabilityDiscovery) section of the standard.

The 2019 specification, <Hint tip="BSV Alias, the working title of the 2019 Paymail specification">bsvalias</Hint>, names two capabilities with words instead of IDs, `pki` and `paymentDestination`, because they were the minimum set a service needed to qualify as a Paymail service. The 2022 standard treats the sections of the 2019 specification as extensions and lists their BRFC IDs:

<BlueTable>

| BRFC ID | Specification |
| --- | --- |
| `0c4339ef99c2` | bsvalias Public Key Infrastructure |
| `a9f510c16bde` | bsvalias Verify Public Key Owner |
| `759684b1a19a` | bsvalias Basic Address Resolution |
| `6745385c3fc0` | bsvalias Payer Validation |
| `3d7c2ca83a46` | bsvalias Payee Approvals |
| `7bd25e5a1fc6` | bsvalias PayTo Protocol Prefix |

</BlueTable>

Hosts built on the 2019 specification, and the `@bsv/paymail` package, still use the key `pki` for public key infrastructure, so a client reads both forms. To know which Paymail capabilities a new app uses, see [Paymail](/standards/paymail/).

## Status of the process

The BRFC process and the ID algorithm come from the 2019 Paymail specification, published as BSV Alias (`bsvalias`). That specification includes a [summary of the process](https://github.com/bitcoin-sv-specs/brfc-paymail/blob/2e03c8bc49b489d13eda7a3580795b1809cd2f08/src/01-brfc-specifications.md).

The current standard is the [Paymail standard](https://tsc.bsvblockchain.org/standards/paymail/) of the Technical Standards Committee, TS 2021.010-30, version 0.1, published on 12 July 2022 with the status Published. It withdraws the 2019 specification as a whole and [uses BRFC IDs](https://tsc.bsvblockchain.org/wp-content/uploads/2022/04/Paymail-_BRFC-IDs-as-element-names.pdf) as the keys of the `capabilities` object for every capability, including the two the 2019 specification named with words. It lists BRFC numbering as a dependency marked "to be standardised", and its own BRFC ID as "TBC". The standard asks extension authors to calculate their BRFC ID and does not define the algorithm, so the steps on this page come from the original 2019 specification.

This page was written against TS 2021.010-30, commit `2e03c8b` of the 2019 specification and `@bsv/paymail` 2.4.12.
