Find which Paymail capabilities a host supports, and the endpoint URL of each one, before your app calls a Paymail service. A Paymail handle such as `alice@example.com` does not say where its services run. The domain owner publishes that in DNS and in a capabilities document, and every Paymail request, such as an identity key lookup, starts by reading them. Read them yourself when you call a Paymail service without a library, debug a handle that does not resolve, or need to know what `@bsv/paymail` does before it sends a request.

## How discovery works

Paymail discovery has two phases. In host discovery, your app finds the host that serves Paymail for the domain in the handle. In capability discovery, that host says what it supports:

<BlueTable>

| Phase | What happens | Details |
| --- | --- | --- |
| Host discovery | Your app splits the handle, such as `alice@example.com`, at `@` into the alias and the domain, and looks up the DNS <Hint tip="Service record, a DNS record that names the host and port of a service">SRV</Hint> record `_bsvalias._tcp.<domain>`. The record names the host and port that serve Paymail, which can belong to a Paymail provider. With no SRV record, the host is the domain itself, on port 443. | [Find the host with a DNS SRV record](#find-the-host-with-a-dns-srv-record) |
| Capability discovery | Your app requests the capabilities document from that host. The host answers with the capabilities it supports and a URL template for each one. Your app fills the template of the capability it needs with the alias and the domain, and calls that URL. | [Read the capabilities document](#read-the-capabilities-document) |

</BlueTable>

### Names in the 2019 and 2022 versions

TS 2021.010-30, published in 2022, withdraws the 2019 specification. It changes the path of the document and the alias token, and keys two capabilities by their <Hint tip="Bitcoin SV Request for Comments, a specification document identified without a central numbering authority">BRFC</Hint> IDs instead of words. The host in the examples below and `@bsv/paymail` 2.4.12 use the 2019 names, and that host answers `404` at `/.well-known/bsvalias.json`:

<BlueTable>

| Name | 2019 specification | 2022 standard |
| --- | --- | --- |
| Path of the capabilities document | `/.well-known/bsvalias` | `/.well-known/bsvalias.json` |
| Alias token in URL templates | `{alias}` | `{local-part}` |
| Key of public key infrastructure | `pki` | `0c4339ef99c2` |
| Key of basic address resolution | `paymentDestination` | `759684b1a19a` |

</BlueTable>

## Find the host with a DNS SRV record

A domain that delegates Paymail to another host publishes an SRV record with these values, as the [2022 standard](https://tsc.bsvblockchain.org/standards/paymail/) defines them:

<BlueTable>

| Parameter | Value |
| --- | --- |
| Service | `_bsvalias` |
| Proto | `_tcp` |
| Class | `IN` |
| Name | The domain of the handle, such as `example.com.` |
| Port | `443` |
| Target | The host that serves Paymail for the domain |
| TTL | `3600` recommended, set by the domain owner |
| Priority and Weight | Set by the domain owner, such as `10` |

</BlueTable>

DNS answers can be forged, so the 2022 standard ties the SRV record to <Hint tip="DNS Security Extensions, signatures that let a resolver check that a DNS answer is authentic">DNSSEC</Hint> and to TLS. It sets these rules for your app:

- An SRV record is a delegation, and a delegation must be served with a valid DNSSEC signature chain. Your app resolves the A or AAAA record of the target and continues with the target as the host. When the target has neither record, host discovery fails.
- Your app ignores an SRV record served without a valid DNSSEC signature chain, and continues with the domain itself as the host.
- When the domain has no SRV record, your app resolves the A or AAAA record of the domain and continues with the domain as the host. When neither record exists, host discovery fails.
- The TLS certificate of the host must be valid and must match the host name your app expects. When it does not match, capability discovery fails. Your app must support TLS and DNSSEC.

The 2019 specification, published as BSV Alias (`bsvalias`), also accepts an SRV record without DNSSEC when its target is the domain itself or `www.<domain>`, and relies on the TLS certificate in that case. Its [Host Discovery](https://github.com/bitcoin-sv-specs/brfc-paymail/blob/2e03c8bc49b489d13eda7a3580795b1809cd2f08/src/02-01-host-discovery.md) section lists the full procedure.

To see a real record, query a DNS over HTTPS resolver from any terminal:

```bash
curl "https://dns.google/resolve?name=_bsvalias._tcp.handcash.io&type=SRV"
```

The resolver returns the record as JSON:

```json
{"Status":0,"TC":false,"RD":true,"RA":true,"AD":true,"CD":false,"Question":[{"name":"_bsvalias._tcp.handcash.io.","type":33}],"Answer":[{"name":"_bsvalias._tcp.handcash.io.","type":33,"TTL":300,"data":"10 100 443 cloud.handcash.io."}],"Comment":"Response from 172.64.33.138."}
```

The `data` field holds the priority, the weight, the port and the target, so Paymail for `handcash.io` runs on `cloud.handcash.io`, port 443. `"AD":true` means the resolver validated the DNSSEC signature chain of the answer, which the 2022 standard requires for a target on another domain. The `Comment` field names the server that answered and changes between requests.

## Read the capabilities document

The host serves the capabilities document over HTTPS, with the status `200`, or `304` when your app sent cache headers and the document has not changed. Request it from the host you found in host discovery:

```bash
curl https://cloud.handcash.io/.well-known/bsvalias
```

The host returns one JSON document:

```json
{"bsvalias":"1.0","capabilities":{"6745385c3fc0":false,"pki":"https://cloud.handcash.io/api/bsvalias/id/{alias}@{domain.tld}","paymentDestination":"https://cloud.handcash.io/api/bsvalias/address/{alias}@{domain.tld}","a9f510c16bde":"https://cloud.handcash.io/api/bsvalias/verifypubkey/{alias}@{domain.tld}/{pubkey}","f12f968c92d6":"https://cloud.handcash.io/api/bsvalias/public-profile/{alias}@{domain.tld}","5f1323cddf31":"https://cloud.handcash.io/api/bsvalias/receive-transaction/{alias}@{domain.tld}","2a40af698840":"https://cloud.handcash.io/api/bsvalias/p2p-payment-destination/{alias}@{domain.tld}","5c55a7fdb7bb":"https://cloud.handcash.io/api/bsvalias/receive-beef/{alias}@{domain.tld}"}}
```

The document has two fields:

- `bsvalias` is the version of the document format, `"1.0"`. The 2019 specification added it for forward compatibility and leaves its interpretation unspecified.
- `capabilities` is an object with one key for each capability the host supports. A key is the BRFC ID of the specification that defines the capability, such as `a9f510c16bde` for Verify Public Key Owner, or one of the two words in the [table of names](#names-in-the-2019-and-2022-versions). [BRFC specification process](/standards/paymail/brfc-specifications/) lists the published IDs.

The specification behind each key defines its value, which takes one of three forms:

- A URL template, the usual form, such as the value of `pki` above.
- A flag, such as `"6745385c3fc0": false`. In Payer Validation, `true` means the host enforces sender validation, and any other value means it does not.
- An object with several fields, such as `{"callback": "https://example.org/{alias}@{domain.tld}/payment-destination-response"}` for Payee Approvals (`3d7c2ca83a46`) in the 2022 standard.

The document describes what the host software supports, not what each account has turned on. A host that lists a capability but has not enabled it for an alias should answer `404` to a request for that alias, the same answer as for an alias that does not exist.

### Fill in a URL template

Replace each placeholder in a template with the matching value, wherever it appears in the URL:

<BlueTable>

| Placeholder | Replace it with | Example value for `alice@example.com` |
| --- | --- | --- |
| `{alias}` | The part of the handle before `@` | `alice` |
| `{local-part}` | The part of the handle before `@`, the name the 2022 standard gives `{alias}` | `alice` |
| `{domain.tld}` | The domain of the handle | `example.com` |
| `{pubkey}` | A compressed public key in hex, in Verify Public Key Owner (`a9f510c16bde`) | The key the app wants to check |

</BlueTable>

For `alice@example.com`, the template `https://example.com/api/bsvalias/id/{alias}@{domain.tld}` becomes `https://example.com/api/bsvalias/id/alice@example.com`. When the host is another domain, the URL still carries the domain of the handle, even though the request goes to the host.

## Discover capabilities with `@bsv/paymail`

The `@bsv/paymail` package runs host discovery and capability discovery in `PaymailClient`. The package needs Node.js 22 or newer. Install it in a Node.js project, with `@bsv/sdk` as its peer dependency:

```bash
npm install @bsv/paymail @bsv/sdk
```

Create this file in the project folder:

```javascript capabilities.mjs
import { PaymailClient } from '@bsv/paymail'

const client = new PaymailClient()

const capabilities = await client.getCapabilities('handcash.io')
console.log(capabilities)

const pkiTemplate = await client.ensureCapabilityFor('handcash.io', 'pki')
console.log(pkiTemplate)
```

Run it with `node capabilities.mjs`. The script only reads public DNS and a public JSON document, so it needs no wallet, no key and no funds, and works the same on any network. It prints the capabilities of the domain, then the URL template of `pki`:

```text
{
  '6745385c3fc0': false,
  pki: 'https://cloud.handcash.io/api/bsvalias/id/{alias}@{domain.tld}',
  paymentDestination: 'https://cloud.handcash.io/api/bsvalias/address/{alias}@{domain.tld}',
  a9f510c16bde: 'https://cloud.handcash.io/api/bsvalias/verifypubkey/{alias}@{domain.tld}/{pubkey}',
  f12f968c92d6: 'https://cloud.handcash.io/api/bsvalias/public-profile/{alias}@{domain.tld}',
  '5f1323cddf31': 'https://cloud.handcash.io/api/bsvalias/receive-transaction/{alias}@{domain.tld}',
  '2a40af698840': 'https://cloud.handcash.io/api/bsvalias/p2p-payment-destination/{alias}@{domain.tld}',
  '5c55a7fdb7bb': 'https://cloud.handcash.io/api/bsvalias/receive-beef/{alias}@{domain.tld}'
}
https://cloud.handcash.io/api/bsvalias/id/{alias}@{domain.tld}
```

The two methods take a domain, not a handle:

- `getCapabilities(domain)` runs both phases and returns the `capabilities` object. `getDomainCapabilities` is the same method under another name.
- `ensureCapabilityFor(domain, code)` returns the URL template of one capability. It throws a `PaymailServerResponseError` with the message `Domain "<domain>" does not support capability "<code>"` when the key is missing or its value is not a string, so a flag such as `6745385c3fc0` throws too. It also rejects a template that is not HTTPS or that points to `localhost`, a `.local` name or an IP address.

The package exports a class for each capability it implements, and `getCode()` returns its key, such as `pki` for `PublicKeyInfrastructureCapability`. Methods such as `getPki` and `verifyPublicKey` run discovery themselves and fill in `{alias}`, `{domain.tld}` and `{pubkey}`, so call them directly when the package implements the capability you need.

### How `PaymailClient` resolves a host

`PaymailClient` 2.4.12 makes these choices, which differ from the 2022 standard in places:

- DNS lookup goes through DNS over HTTPS (DoH), at `https://dns.google.com/resolve` by default. The second argument of the constructor takes `dohServerBaseUrl` to use another resolver, or `dns`, an object with a `resolveSrv` function such as the `node:dns` module, which `PaymailClient` tries first. It uses a `dns` answer only when the target is the domain or one of its subdomains, and asks the DoH resolver otherwise.
- With the default DoH resolver, the fallback to the domain on port 443 happens only when the resolver answers that the SRV name does not exist. Other answers without an SRV record, such as an empty answer, fail with `<domain> is not correctly configured: insecure domain`.
- An SRV record without DNSSEC is accepted when the target is the domain or one of its subdomains. For a target on another domain without DNSSEC, `PaymailClient` fails with the same `insecure domain` error, where the 2022 standard falls back to the domain.
- The document request goes to `https://<host>:<port>/.well-known/bsvalias` over HTTPS only, does not follow redirects, stops after 30 seconds, and reads at most 1 MiB. A response with an error status throws a `PaymailServerResponseError` that carries the response body.
- Capabilities are cached for five minutes per domain in the `PaymailClient` instance, for up to 256 domains, and calls for the same domain at the same time share one request. Reuse one `PaymailClient` to keep the cache.
- For local development, the domain `localhost` skips DNS and is requested over HTTP on port 3000, or on the port given as the third argument of the constructor.
- The package methods replace only `{alias}`, `{domain.tld}` and `{pubkey}`, and look up the key `pki`, not `0c4339ef99c2`. For a host that uses `{local-part}` or lists only the BRFC ID of PKI, read the document and fill in the template yourself.

<Callout type="warning">
`@bsv/paymail` 2.4.12 accepts only a document whose `bsvalias` is exactly `"1.0"` and whose capability values are strings or booleans. A host that lists one capability with an object value, such as Payee Approvals in the 2022 standard, makes `getCapabilities` and every method that depends on it fail with `Validation error: capability values must be bounded strings or booleans`. To read such a host, request the document yourself as in [Read the capabilities document](#read-the-capabilities-document).
</Callout>

This page was written against the 2022 standard, TS 2021.010-30, commit `2e03c8b` of the 2019 specification and `@bsv/paymail` 2.4.12 with `@bsv/sdk` 4.0.1. The script ran on Node.js 24.19.0, and the outputs on this page are from 4 November 2026. A host can change its document at any time, so your output can differ.
