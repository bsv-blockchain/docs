Basic Address Resolution turns a Paymail handle such as `alice@example.com` into the <Hint tip="The part of a transaction output that sets the condition to spend it">locking script</Hint> a payment to that user must use. The sender sends a request to the host of the handle, and the host answers with the locking script in hex. The capability belongs to the 2019 payment addressing capabilities, which are not recommended for new apps. Payments in new apps go through the user's <Hint tip="BSV Request for Comments 100, the standard interface between a wallet and an app">BRC-100</Hint> wallet. Use this page to build the request for a host that still serves the capability and to check the locking script it returns.

## Find the endpoint

The host lists Basic Address Resolution in its capabilities document under one of two keys, and the value is a URL template:

<BlueTable>

| Version | Key | Alias token in the template |
| --- | --- | --- |
| 2019 specification | `paymentDestination` | `{alias}` |
| 2022 standard, TS 2021.010-30 | `759684b1a19a`, the <Hint tip="Bitcoin SV Request for Comments, a specification document identified without a central numbering authority">BRFC</Hint> ID | `{local-part}` |

</BlueTable>

The [2022 standard](https://tsc.bsvblockchain.org/standards/paymail/) withdraws the 2019 specification and treats Basic Address Resolution as an extension. In both versions, the alias token takes the part of the handle before `@`, and `{domain.tld}` takes its domain. [Discover Paymail capabilities](/standards/paymail/capability-discovery/) covers how to find the host, read the document and fill in a template.

## Request

The sender sends an HTTP `POST` request to the filled URL, with the content type `application/json`. This example body follows the 2019 specification. Replace `SENDER_HANDLE` with the sender's Paymail handle, `ISO_8601_TIMESTAMP` with the time of the request and `MESSAGE_SIGNATURE` with the signature described in [Sender validation](#sender-validation):

```json
{
  "senderName": "FirstName LastName",
  "senderHandle": "SENDER_HANDLE",
  "dt": "ISO_8601_TIMESTAMP",
  "amount": 550,
  "purpose": "message to receiver",
  "signature": "MESSAGE_SIGNATURE"
}
```

The specification defines each field:

<BlueTable>

| Field | Required | Value |
| --- | --- | --- |
| `senderName` | No | The display name of the sender |
| `senderHandle` | Yes | The Paymail handle of the sender |
| `dt` | Yes | The time of the request, as an ISO 8601 timestamp such as `2013-10-21T13:28:06.419Z` |
| `amount` | No | The amount the sender intends to pay, in satoshis (100,000,000 satoshis make 1 BSV) |
| `purpose` | No | A description of the payment for the receiver |
| `signature` | Only when the host enforces sender validation | A compact Bitcoin message signature over the request |

</BlueTable>

## Response

The host answers `200` for a handle it knows, with the content type `application/json` and an `output` field that holds the locking script in hex. The sender must use that script in an output of the payment transaction. The 2019 specification gives this example, a <Hint tip="Pay to Public Key Hash, a locking script spent with a signature from the key whose hash it holds">P2PKH</Hint> script:

```json
{
  "output": "76a9140806efc8bedc8afb37bf484f352e6f79bff1458c88ac"
}
```

The specification expects hosts to support at least P2PKH scripts. A `404` means the host does not know the handle. Any status code the specification does not define, such as a `5xx` server error, counts as a transient error, and the request may be retried.

## Sender validation

Sender validation is defined in Payer Validation, an extension with the BRFC ID `6745385c3fc0`. A host enforces it when its capabilities document sets that key to `true`, and any other value means it does not. When it is in force:

- The request must carry the `signature` field. The 2019 specification defines the signed message as the UTF-8 concatenation of `senderHandle`, `dt`, `amount` and `purpose`, in that order. The `amount` field is a string with no leading zeros, or `"0"` when there is no amount, and the `purpose` field is an empty string when there is none. The `go-paymail` library v0.28.0 signs them in the order `senderHandle`, `amount`, `dt`, `purpose`, so check which order the host verifies. The message is signed with the Bitcoin Signed Message scheme: `@bsv/paymail` 2.4.12 prefixes the message with `Bitcoin Signed Message:\n`, hashes it and encodes the compact signature in base64.
- The host looks up the public key of `senderHandle` through public key infrastructure (`pki`), the Paymail capability that returns the public key of a handle. It answers `401` when it cannot resolve a key, when the signature is missing or invalid, or when `dt` is more than two minutes away from its own clock, which limits replayed requests.
- The `200` response adds a `signature` field, a Bitcoin message signature over the UTF-8 text of `output`. The sender verifies it against the receiver's public key before it uses the script. It gets that key through `pki`, for example with `getPki` of `@bsv/paymail`.

The 2022 standard states that it modifies the message signing process of the 2019 specification, and it defines no signature scheme of its own: it leaves the choice to each extension.

A host built with `@bsv/paymail` 2.4.12 can list `6745385c3fc0` for another reason. The package README states that its router derives this flag from its transaction receive routes, and that the flag does not prove payer validation, timestamp checks or replay protection as Payer Validation defines them.

## Trust in the returned script

The response signature protects the locking script against changes in transit. It does not protect against a compromised host: the receiver's public key comes from the same host, so a host under an attacker's control can sign a script of its own. The 2022 standard lists hijacked or compromised hosts among its risks and gives no specific mitigation. Without sender validation, the sender relies only on the host checks of discovery, <Hint tip="DNS Security Extensions, signatures that let a resolver check that a DNS answer is authentic">DNSSEC</Hint> for a delegated domain and a valid <Hint tip="Transport Layer Security, the encryption and certificate check behind HTTPS">TLS</Hint> certificate that matches the host. A payment sent to a substituted locking script cannot be undone.

## Support in `@bsv/paymail`

The `@bsv/paymail` package 2.4.12 has no dedicated method for Basic Address Resolution, and `PaymailRouter` serves no route for it. It implements P2P Payment Destination (`2a40af698840`) instead, through `getP2pPaymentDestination(paymail, satoshis)`, as specified in [BRC-28](https://github.com/bsv-blockchain/BRCs/blob/fb14783720bbb90cf3cb1893f1b28a074db61f55/payments/0028.md). BRC-28 notes that the BRC-100 wallets of `@bsv/sdk` and `@bsv/wallet-toolbox` do not implement Paymail destination discovery. It also notes that new wallet integrations use BRC-100 payment construction and remittance flows, such as BRC-29, unless they need Paymail interoperability.
