On BSV, a private key proves control. It signs the inputs that spend an output and the messages an app sends, and the matching public key lets anyone check those signatures. A wallet holds the keys for your app. You work with them when you derive a key for another party, identify a user or debug a failed signature.

The examples use `@bsv/sdk` 4.0.1 and run with Node.js. Install it with `npm install @bsv/sdk@4.0.1`, save each example as an `.mjs` file and run it with `node`. [How the BSV stack fits together](/concepts/architecture/) shows where the wallet sits.

## Private keys, public keys and addresses

A private key is a 256 bit number. The public key is computed from it on the secp256k1 curve and is 33 bytes when compressed, so you can share it. An address is the <Hint tip="SHA-256 followed by RIPEMD-160">hash160</Hint> of the public key with a version byte and a checksum added, and the version byte tells testnet from Mainnet.

### Sign and verify in code

<Callout type="warning">
Each example generates a new random private key on every run, only to try the code. Never put a private key that holds value in code, and never commit one to version control.
</Callout>

```javascript keys.mjs
import { PrivateKey, Hash, Utils } from '@bsv/sdk'

const privateKey = PrivateKey.fromRandom()
const publicKey = privateKey.toPublicKey()

console.log('public key:', publicKey.toString())
console.log('address:', publicKey.toAddress('testnet'))

const message = Utils.toArray('Hi Bob', 'utf8')
const signature = privateKey.sign(message)
console.log('verifies:', publicKey.verify(message, signature))
console.log('changed message verifies:', publicKey.verify(Utils.toArray('Hi Eve', 'utf8'), signature))

console.log('sha256:', Utils.toHex(Hash.sha256(message)))
console.log('hash160:', Utils.toHex(Hash.hash160(publicKey.encode(true))))
```

The keys and the address differ on every run. The signature verifies only for the message it signed and only with the public key that matches the private key that signed it:

```text
public key: 027c63fbcc252f2a9f6a12cde260e8cbc0173d7ecbf9f82856bf13e93982a93158
address: moA1VC9hp5a5g5EkxhRJmFidGWtYEAuVWB
verifies: true
changed message verifies: false
sha256: 18bdc796d44d1dbcc0c5b28022c0f8660b2a7c312ce612025468826c5e5a630e
hash160: 53caef87a9712734119b97d176b45d8d8a7299db
```

The locking script of a payment to an address holds that hash160. [How Script works](/concepts/script/) shows how the network checks the public key and signature that spend it.

## Hash functions

`@bsv/sdk` has `Hash.sha256` (32 bytes), `Hash.ripemd160` (20 bytes), `Hash.hash160` and `Hash.hash256`, which is SHA-256 applied twice. The address above is a hash160, and the last two lines of `keys.mjs` print a SHA-256 and a hash160.

## Derived keys

An app that signs everything with one key ties all its activity to that key. BRC-42 gives two parties a way to derive a separate key for each other, and for each purpose, from keys they already have. The earlier docs call it type 42.

### How two parties derive a key

Each party keeps a master private key and shares the master public key. To derive a key, they agree on an invoice number, which is any string that names the purpose, such as `order 1042`. The derivation has three steps:

1. Each party combines its own private key with the other's public key. Both get the same shared secret, using <Hint tip="Elliptic curve Diffie-Hellman, a way for two parties to compute the same secret from their own private key and the other's public key">ECDH</Hint>.
2. The shared secret is the key of an <Hint tip="Hash based message authentication code">HMAC</Hint> over the invoice number.
3. The owner adds the result to the master private key to get the child private key. The other party adds it to the owner's master public key to get the matching child public key.

<Visibility for="agents">
The diagram has Alice on the left, Bob on the right and what both sides share in the middle. Step 1, each holds a master private key and the other's public key. Step 2, both compute the same shared secret. Step 3, both run an HMAC over the invoice number order 1042 keyed by the shared secret and get equal results. Step 4, Alice adds the result to her master private key to get the child private key, and Bob adds it to her master public key to get the matching child public key, and the two match. Step 5, Alice signs with the child private key and Bob verifies the signature with the child public key. If Bob uses another invoice number or another private key, the results at step 2 or 3 differ, the keys do not match and the signature does not verify.
</Visibility>

### Derive keys in code

```javascript derive.mjs
import { PrivateKey, Utils } from '@bsv/sdk'

const alice = PrivateKey.fromRandom()
const bob = PrivateKey.fromRandom()
const invoiceNumber = 'order 1042'

// Alice derives a private key for Bob to check, using only Bob's public key.
const aliceChild = alice.deriveChild(bob.toPublicKey(), invoiceNumber)
const signature = aliceChild.sign(Utils.toArray('Hi Bob', 'utf8'))

// Bob derives the matching public key from Alice's public key and his own private key.
const aliceChildPublic = alice.toPublicKey().deriveChild(bob, invoiceNumber)

console.log('keys match:', aliceChild.toPublicKey().toString() === aliceChildPublic.toString())
console.log('Bob verifies:', aliceChildPublic.verify(Utils.toArray('Hi Bob', 'utf8'), signature))

// A different invoice number gives a different key.
const other = alice.toPublicKey().deriveChild(bob, 'order 1043')
console.log('other invoice, same key:', other.toString() === aliceChildPublic.toString())

// Someone with a different private key derives a different key, which does not verify.
const eve = PrivateKey.fromRandom()
const eveGuess = alice.toPublicKey().deriveChild(eve, invoiceNumber)
console.log('Eve verifies:', eveGuess.verify(Utils.toArray('Hi Bob', 'utf8'), signature))
```

```text
keys match: true
Bob verifies: true
other invoice, same key: false
Eve verifies: false
```

Bob never sees Alice's private key, and each pair of parties has its own set of derived keys. This differs from <Hint tip="The standard for hierarchical wallets that derive child keys from one master key">BIP32</Hint>, where anyone holding an extended public key can derive its non hardened public child keys. The invoice number is not secret. What the derivation needs is the shared secret.

## How a wallet organizes derived keys

BRC-43 gives the invoice number a format that a wallet can enforce, `<security level>-<protocol name>-<key ID>`, for example `2-order receipts-1042`. BRC-43 defines what each security level asks the user to approve:

- Level 0 needs no approval.
- Level 1 asks once per app and protocol.
- Level 2 asks once for each counterparty as well.

The counterparty is `self`, `anyone` or the public key of another party. With `self`, the wallet derives from its own key, for data only the user needs. With `anyone`, the derivation uses a publicly known private key (the number 1), so anyone can derive the same public key. `ProtoWallet` in `@bsv/sdk` does the derivation and checks the names, and a wallet adds the approval prompts. The [BRC-100 Wallet Interface](/concepts/wallet-model/) has the same calls, `getPublicKey`, `createSignature`, `verifySignature`, `encrypt` and `decrypt`. The derived key signs and it encrypts, and the last lines of the example show both.

### Sign and encrypt with a wallet

```javascript wallet.mjs
import { PrivateKey, ProtoWallet, Utils } from '@bsv/sdk'

const alice = new ProtoWallet(PrivateKey.fromRandom())
const bob = new ProtoWallet(PrivateKey.fromRandom())

const aliceIdentity = (await alice.getPublicKey({ identityKey: true })).publicKey
const bobIdentity = (await bob.getPublicKey({ identityKey: true })).publicKey

// protocolID is [security level, protocol name], and the key ID picks one key inside it.
const protocolID = [2, 'order receipts']
const keyID = '1042'
const data = Utils.toArray('Order 1042 received', 'utf8')

const { signature } = await alice.createSignature({ data, protocolID, keyID, counterparty: bobIdentity })
const { valid } = await bob.verifySignature({ data, signature, protocolID, keyID, counterparty: aliceIdentity })
console.log('Bob verifies:', valid)

// The same wallet holds a different key for each counterparty.
for (const counterparty of ['self', 'anyone', bobIdentity]) {
  const { publicKey } = await alice.getPublicKey({ protocolID, keyID, counterparty })
  console.log(counterparty === bobIdentity ? 'Bob' : counterparty, publicKey.slice(0, 12) + '...')
}

// The same derivation encrypts, and only the counterparty can decrypt.
const { ciphertext } = await alice.encrypt({ plaintext: data, protocolID, keyID, counterparty: bobIdentity })
const { plaintext } = await bob.decrypt({ ciphertext, protocolID, keyID, counterparty: aliceIdentity })
console.log('Bob decrypts:', Utils.toUTF8(plaintext))
```

```text
Bob verifies: true
self 03e081bd8e89...
anyone 03bed2a7e407...
Bob 0278068d14d6...
Bob decrypts: Order 1042 received
```

A signature made under one protocol name or key ID does not verify under another. `ProtoWallet` and `KeyDeriver` also check the name. A protocol name has at least 5 characters, no double spaces and does not end in "protocol", and BRC-43 sets further limits on characters and length. So `order receipts protocol` throws `No need to end your protocol name with " protocol"`. `PrivateKey.deriveChild` does not run these checks, it takes any string.

## Identity keys and mutual authentication

The identity key is the wallet's root public key, 33 bytes. It stays the same across calls, and the keys derived for protocols are different from it. An app reads it with `getPublicKey({ identityKey: true })`, as in the example, and uses it to recognize a user and to check who a request comes from.

Two parties prove their identity keys to each other in a handshake. The BRC-103 standard defines this exchange between peers, and BRC-104 binds it to HTTP. `AuthFetch` in `@bsv/sdk` is the client side, and `@bsv/auth-express-middleware` is the server side, where each request arrives with the user's identity key in `req.auth.identityKey`. [Authenticate users with their wallet](/guides/identity-auth/) walks through the steps. The identity covers the method, path, query, signed headers and body of a request, not the `Host` header or cookies. BRC-31 is historical guidance and not the current HTTP contract.

Certificates build on the same keys. A certifier signs a certificate that binds fields to a user's identity key, and a changed field no longer verifies.
