On BSV, a private key proves control. It signs the inputs that spend an output and the messages an app sends, and the matching public key lets anyone check those signatures. A wallet holds the keys for your app. You work with them when you derive a key for another party, identify a user or debug a failed signature.

The examples use `@bsv/sdk` 4.0.1 and run with Node.js. Install it with `npm install @bsv/sdk@4.0.1`, save each example as an `.mjs` file and run it with `node`. [How the BSV stack fits together](/concepts/architecture/) shows where the wallet sits.

## Private keys, public keys and addresses

A private key is a 256 bit number, and the public key and the address are computed from it.

### From a private key to an address

Select **Private key**, **Public key**, **hash160** and **Address** in turn to see what each one is and how it is made, then switch between **Testnet** and **Mainnet** to see what changes in the address.

<KeyPairFlow />

<Visibility for="agents">
The diagram has four stages in a row, joined by one way arrows. The private key is a 256 bit number of 32 bytes that signs and is never shared. The public key is 33 bytes when compressed, made from the private key on the secp256k1 curve, and can be shared. The hash160 is 20 bytes, a SHA-256 of the public key followed by a RIPEMD-160, and it is what a P2PKH locking script holds. The address is 25 bytes, a version byte, the hash160 and a 4 byte checksum written in base58. The version byte is 0x00 on Mainnet, so the address starts with 1, and 0x6f on testnet, so it starts with m or n.
</Visibility>

### Sign and verify in code

This example creates a key pair, signs a message and checks the signature, then prints the hash160 of the public key.

<Callout type="warning">
Each example generates a new random private key on every run, only to try the code. Never put a private key that holds value in code, and never commit one to version control.
</Callout>

```javascript keys.mjs
import { PrivateKey, Hash, Utils } from '@bsv/sdk'

const privateKey = PrivateKey.fromRandom()
const publicKey = privateKey.toPublicKey()

console.log('public key:', publicKey.toString())
console.log('address:', publicKey.toAddress('testnet'))

const message = Utils.toArray('Hi John', 'utf8')
const signature = privateKey.sign(message)
console.log('verifies:', publicKey.verify(message, signature))
console.log('changed message verifies:', publicKey.verify(Utils.toArray('Hi Eve', 'utf8'), signature))

console.log('hash160:', Utils.toHex(Hash.hash160(publicKey.encode(true))))
```

The signature verifies for the message it signed with the matching public key, and fails for a changed message or for another public key:

```text
public key: 0273fdc6002ad4fc59d1a9a9cdb11a8da48a8e00cc7e557a2426fd0d8bb0a57e87
address: n2wE7d97xdfHCNYjnjRCDf7PKV1J8SekN7
verifies: true
changed message verifies: false
hash160: eaf1d49f4c640a75f6da33e06aec862a43346806
```

[How Script works](/concepts/script/) shows how the network checks the public key and signature that spend an output locked to that hash.

## Hash functions

`@bsv/sdk` has `Hash.sha256` (32 bytes), `Hash.ripemd160` (20 bytes), `Hash.hash160` and `Hash.hash256`, which is SHA-256 applied twice.

## Derived keys

An app that signs everything with one key ties all its activity to that key. <Hint tip="The standard for deriving a separate key for each pair of parties">BRC-42</Hint> gives two parties a way to derive a separate key for each other, and for each purpose, from keys they already have.

### How two parties derive a key

Each party keeps a master private key and shares the master public key. The two agree on an invoice number, any string that names the purpose, such as `order 1042`. Both get the same shared secret through <Hint tip="Elliptic curve Diffie-Hellman, a way for two parties to compute the same secret from their own private key and the other's public key">ECDH</Hint> and run an <Hint tip="Hash based message authentication code">HMAC</Hint> over the invoice number with it. The owner adds the result to the master private key to get the child private key. The other party adds it to the owner's master public key to get the matching child public key.

Press **Step** to follow Jane and John to the same child key, then switch to **Another invoice number** or **Another private key** and run it again to watch the check fail.

<DeriveSteps />

<Visibility for="agents">
The diagram has Jane on the left, John on the right and what both sides share in the middle. Step 1, each holds a master private key and the other's public key. Step 2, both compute the same shared secret. Step 3, both run an HMAC over the invoice number order 1042 keyed by the shared secret and get equal results. Step 4, Jane adds the result to her master private key to get the child private key, and John adds it to her master public key to get the matching child public key, and the two match. Step 5, Jane signs with the child private key and John verifies the signature with the child public key. If John uses another invoice number or another private key, the results at step 2 or 3 differ, the keys do not match and the signature does not verify.
</Visibility>

### Derive keys in code

Jane derives a private key for John from his public key and signs with it. John derives the matching public key from hers and checks the signature, then the example repeats the derivation with another invoice number and with another private key.

```javascript derive.mjs
import { PrivateKey, Utils } from '@bsv/sdk'

const jane = PrivateKey.fromRandom()
const john = PrivateKey.fromRandom()
const invoiceNumber = 'order 1042'

const janeChild = jane.deriveChild(john.toPublicKey(), invoiceNumber)
const signature = janeChild.sign(Utils.toArray('Hi John', 'utf8'))

const janeChildPublic = jane.toPublicKey().deriveChild(john, invoiceNumber)

console.log('keys match:', janeChild.toPublicKey().toString() === janeChildPublic.toString())
console.log('John verifies:', janeChildPublic.verify(Utils.toArray('Hi John', 'utf8'), signature))

const other = jane.toPublicKey().deriveChild(john, 'order 1043')
console.log('other invoice, same key:', other.toString() === janeChildPublic.toString())

const eve = PrivateKey.fromRandom()
const eveGuess = jane.toPublicKey().deriveChild(eve, invoiceNumber)
console.log('Eve verifies:', eveGuess.verify(Utils.toArray('Hi John', 'utf8'), signature))
```

```text
keys match: true
John verifies: true
other invoice, same key: false
Eve verifies: false
```

John never sees Jane's private key, and each pair of parties has its own set of derived keys. This differs from <Hint tip="The standard for hierarchical wallets that derive child keys from one master key">BIP32</Hint>, where anyone holding an extended public key can derive its non hardened public child keys. The invoice number is not secret. What the derivation needs is the shared secret.

## How a wallet organizes derived keys

<Hint tip="The standard format for invoice numbers: a security level, a protocol name and a key ID">BRC-43</Hint> gives the invoice number a format that a wallet can enforce, `<security level>-<protocol name>-<key ID>`, for example `2-order receipts-1042`. The security level and the counterparty decide which key the wallet derives and what it asks the user to approve. `ProtoWallet` in `@bsv/sdk` does the derivation and checks the names through its `KeyDeriver`. BRC-43 leaves the approval prompts to the wallet. The [BRC-100 Wallet Interface](/concepts/wallet-model/) covers the wallet calls for keys and encryption.

### Build an invoice number

Move the **Security level** from 0 to 2 and pick a **Counterparty** to see what each one means, then edit the **Protocol name** and the **Key ID** to watch the invoice number change. Try a name that ends in "protocol" or has fewer than five characters to see a check fail.

<InvoiceBuilder />

<Visibility for="agents">
The tool joins a security level of 0, 1 or 2, a protocol name and a key ID with hyphens, for example 2-order receipts-1042, and lists the checks of KeyDeriver in @bsv/sdk 4.0.1. The name is trimmed and lowercased in the invoice number. The protocol name has 5 to 400 characters after trimming, only letters, numbers and spaces, no double spaces, and does not end in protocol. The key ID has at least 1 character. The counterparty is self, which derives from the wallet's own key, anyone, which uses the publicly known private key 1 so that anyone can derive the same public key, or another party, whose identity public key the wallet needs. Level 0 asks the user for nothing, level 1 asks once for the app and the protocol, and level 2 asks once for the app, the protocol and each counterparty. BRC-43 says 280 characters for the name, and the SDK accepts up to 400.
</Visibility>

### Sign and encrypt with a wallet

Two `ProtoWallet` instances stand in for the wallets of Jane and John. Jane signs and encrypts a message for John under the invoice number from the builder, and John verifies and decrypts it.

```javascript wallet.mjs
import { PrivateKey, ProtoWallet, Utils } from '@bsv/sdk'

const jane = new ProtoWallet(PrivateKey.fromRandom())
const john = new ProtoWallet(PrivateKey.fromRandom())

const janeIdentity = (await jane.getPublicKey({ identityKey: true })).publicKey
const johnIdentity = (await john.getPublicKey({ identityKey: true })).publicKey

// protocolID is [security level, protocol name], and the key ID picks one key inside it.
const protocolID = [2, 'order receipts']
const keyID = '1042'
const data = Utils.toArray('Order 1042 received', 'utf8')

const { signature } = await jane.createSignature({ data, protocolID, keyID, counterparty: johnIdentity })
const { valid } = await john.verifySignature({ data, signature, protocolID, keyID, counterparty: janeIdentity })
console.log('John verifies:', valid)

for (const counterparty of ['self', 'anyone', johnIdentity]) {
  const { publicKey } = await jane.getPublicKey({ protocolID, keyID, counterparty })
  console.log(counterparty === johnIdentity ? 'John' : counterparty, publicKey.slice(0, 12) + '...')
}

const { ciphertext } = await jane.encrypt({ plaintext: data, protocolID, keyID, counterparty: johnIdentity })
const { plaintext } = await john.decrypt({ ciphertext, protocolID, keyID, counterparty: janeIdentity })
console.log('John decrypts:', Utils.toUTF8(plaintext))
```

```text
John verifies: true
self 03e081bd8e89...
anyone 03bed2a7e407...
John 0278068d14d6...
John decrypts: Order 1042 received
```

A signature made under one protocol name or key ID does not verify under another. `ProtoWallet` rejects an invalid name, so `order receipts protocol` throws `No need to end your protocol name with " protocol"`. `PrivateKey.deriveChild` does not run these checks, it takes any string.

## Identity keys and mutual authentication

The identity key is the root public key of the wallet. It stays the same across calls and differs from the keys derived for protocols. An app reads it with `getPublicKey({ identityKey: true })` and uses it to recognize a user.

### A request with and without authentication

Two parties prove their identity keys to each other in a handshake. <Hint tip="The standard for mutual authentication between peers">BRC-103</Hint> defines this exchange between peers, and <Hint tip="The standard that binds BRC-103 to HTTP">BRC-104</Hint> binds it to HTTP. `AuthFetch` in `@bsv/sdk` is the client, and `@bsv/auth-express-middleware` is the server. Follow a request from the app to the server with **Step**, then switch to **A plain fetch** to see the server turn it away. [Authenticate users with their wallet](/guides/identity-auth/) walks through the setup.

<IdentityRequest />

<Visibility for="agents">
The diagram has the app on the left, the Express server on the right and the result in the middle. With AuthFetch, the app and the server first prove their identity keys to each other in a handshake. The request then goes out signed with the identity key of the app. The middleware verifies the signature and puts the identity key in req.auth.identityKey, and the route runs. The response is signed too and carries the identity key of the server in the x-bsv-auth-identity-key header, and the app gets status 200. With a plain fetch, the request has no identity key and no signature, the middleware turns it away, and the server answers 401 with the code UNAUTHORIZED and the message Mutual-authentication failed!
</Visibility>

### What the identity covers

In the BRC-104 v0.1 binding, as the ts-stack identity page describes it, the signature covers some parts of a request and not others:

| Covered | Not covered |
|---------|-------------|
| Method, path and query | `Host` header |
| Declared signed headers and body | Cookies and most other headers |

Authorize with the authenticated identity key and the covered parts only. BRC-31 is historical guidance, not the current HTTP contract.

### Certificates

A certifier signs a certificate that binds fields to the identity key of a user, and the fields are encrypted. The certificate verifies, and it no longer verifies if a field changes.
