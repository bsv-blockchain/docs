<Hint tip="Background Evaluation Extended Format (BRC-62)">BEEF</Hint> is the binary format BSV uses to send a transaction together with the proof that the outputs it spends exist in the chain. An app or wallet that receives a BEEF checks that proof against block headers it already has, instead of asking a node about the transaction. This check is called <Hint tip="Simplified Payment Verification (BRC-67)">SPV</Hint>.

## How an app verifies a transaction without a node

A receiver verifies a BEEF in three checks, and the first one proves that a transaction is in a block.

### The proof

<Visibility for="agents">
The diagram shows a block of eight transactions as a Merkle tree, with the block header above the root. Selecting a transaction marks the three hashes its BUMP keeps, which are the siblings along the path to the root. Playing the animation hashes the transaction ID with its first sibling, then with the next sibling, then once more to reach the computed Merkle root. A switch sets whether the root in the block header matches the computed root. When it matches, the transaction is in the block. When it does not, the BEEF is rejected and nothing else in it is read. A block of 4,096 transactions would need 12 hashes, not 4,096.
</Visibility>

A block header commits to every transaction in its block through the Merkle root, so a <Hint tip="The chain of hashes that links one transaction to the Merkle root of its block">Merkle path</Hint> from a transaction up to that root proves it is in the block. The receiver needs the headers to check it, not the blocks. A block of 4,096 transactions would need 12 hashes, not 4,096.

### The three checks

An app that receives a BEEF runs three checks, in this order:

<Steps>
  <Step title="Compute the roots">
    The app computes one Merkle root for each BUMP in the BEEF.
  </Step>
  <Step title="Check the headers">
    The app asks a <Hint tip="The part of the SDK that checks a Merkle root against the block headers of a network">chain tracker</Hint> whether each root belongs to the block at the height in its BUMP. If one does not, the BEEF is rejected and nothing else is checked.
  </Step>
  <Step title="Check the transactions without a proof">
    For each of these, the app confirms that its inputs spend outputs of transactions it has already verified, that every script evaluates to true, and that the <Hint tip="The smallest unit of BSV. 100,000,000 satoshis make 1 BSV">satoshis</Hint> in cover the satoshis out plus the fee.
  </Step>
</Steps>

<Callout type="warning">
  A BEEF shows that the transaction spends outputs that exist in a block and that its scripts pass. It does not show that nobody spent those outputs in another transaction. [BRC-62](https://bsv.brc.dev/transactions/0062) names this limit and describes the format as intended for micropayments, where the risk is low.
</Callout>

## What is inside a BEEF

A BEEF is a list of Merkle paths, called BUMPs, followed by a list of transactions.

### Layout and order

The diagram shows one BEEF that carries a single payment, as the chain the receiver checks and as the bytes that carry it. Select any part to see what it is and where it sits in the other row.

<BeefAnatomy />

<Visibility for="agents">
The diagram has two rows. The top row is the chain the receiver checks, left to right. The block header is held by the receiver, and the root in the BUMP must match it. The BUMP proves the parent transaction is in the block. The parent transaction's output is spent by the payment transaction, which is the one being sent. The bottom row is the BEEF in byte order. It starts with the 4 byte version 0100beef, then 01 for one BUMP, the BUMP itself, then 02 for two transactions. The counts are VarInts of 1 to 9 bytes. The parent transaction follows with the flag 01 00, which says it has BUMP number 0. The payment transaction comes last with the flag 00, which says it has no BUMP. The BUMP, the parent transaction and the payment transaction share a color in both rows. Selecting a part in either row highlights it in both rows and explains it, including the version, the BUMP count and the transaction count.
</Visibility>

The Merkle paths come first and each transaction comes after the ones it spends, so a receiver can start verifying from the first bytes, before the whole BEEF has arrived.

### Merkle paths

Each BUMP records the height of the block, which tells the receiver which header to compare against. It then records, level by level, only the hashes needed to reach the Merkle root, the ones marked in amber in the tree under The proof.

One BUMP can hold the paths of several transactions in the same block and share the hashes they have in common. A BEEF with two mined ancestors from the same block therefore carries one BUMP, not two.

### Ancestors

Each input of a transaction spends an output of an earlier transaction, so verifying the transaction means following its inputs back. A BEEF carries those earlier transactions up to the first ones that have a Merkle path. A mined ancestor brings its BUMP and none of its own parents. A transaction that spends unconfirmed outputs brings those parents as well, until every branch ends at a mined transaction.

A BEEF whose oldest transactions have no Merkle path has nothing to anchor to, and it does not verify.

## BEEF forms and where each one is used

Three forms of BEEF are in use. They share the same Merkle paths and transactions and differ in the prefix and in what they allow, and each BSV interface picks one of them.

### The three forms

| Form | BRC | Starts with | What it is |
|---|---|---|---|
| BEEF V1 | [BRC-62](https://bsv.brc.dev/transactions/0062) | `0100beef` | The Merkle paths first, then the transactions in order, each with a flag for its BUMP |
| BEEF V2 | [BRC-96](https://bsv.brc.dev/transactions/0096) | `0200beef` | A format byte before each transaction: `00` for a raw transaction, `01` for a raw transaction with a BUMP index and `02` for a transaction ID only. A BEEF can hold several separate transaction trees |
| Atomic BEEF | [BRC-95](https://bsv.brc.dev/transactions/0095) | `01010101`, then the ID of the subject transaction | A complete BEEF whose transactions are all in the ancestry of the subject transaction. Nothing unrelated is allowed |

An entry with only a transaction ID stands for a transaction the receiver already verified. In `@bsv/sdk` it counts only when you pass `true` as the `allowTxidOnly` argument of `isValid` or `verify`, for example `beef.verify(tracker, true)`. Without it, the BEEF does not verify.

In an Atomic BEEF, `@bsv/sdk` writes the transaction ID in the prefix in the byte order of the serialized transaction, which is the reverse of the ID as an explorer shows it.

### Where each form is used

A wallet makes and reads BEEFs for the app, so an app rarely builds one itself. Each interface below uses one form:

| Where | Form |
|---|---|
| `tx` in the result of `createAction`, and `tx` in `internalizeAction`, in <Hint tip="The standard interface between an app and a wallet">BRC-100</Hint> | Atomic BEEF |
| `inputBEEF` in `createAction` | BEEF |
| The request body when you submit a transaction to an <Hint tip="Built from topic managers, which decide what is admitted, and lookup services, which query what was admitted.">overlay service</Hint>, in [BRC-22](https://bsv.brc.dev/overlays/0022) | BEEF |
| A payment between two parties, in [BRC-29](https://bsv.brc.dev/payments/0029) | Atomic BEEF |
| The `x-bsv-beef` header of an HTTP 402 payment, in [BRC-121](https://bsv.brc.dev/payments/0121), encoded as base64 | Atomic BEEF |

## Read and make a BEEF with the SDK

The examples were written against `@bsv/sdk` 4.0.1 and run on testnet.

### Read and verify a BEEF

To read a BEEF and check it against the block headers of testnet:

```typescript
import { Beef, Utils, WhatsOnChain } from '@bsv/sdk'

const beefHex = 'BEEF_HEX' // replace with a testnet BEEF as hex, for example from a wallet or a request

const beef = Beef.fromBinary(Utils.toArray(beefHex, 'hex'))
const isValid = await beef.verify(new WhatsOnChain('test'))
console.log(isValid)
```

For a BEEF whose Merkle roots match the testnet headers, it prints:

```text
true
```

- `Beef.fromBinary` reads V1, V2 and Atomic BEEF. Compare `beef.version` with `BEEF_V1` and `BEEF_V2` to tell which version it is.
- `verify` returns `false` when a root does not match a header and when the BEEF has no Merkle path to anchor to. It covers the first two checks above and the link between each transaction and its inputs. It does not evaluate scripts or compare satoshis, so `true` is not proof that a payment is valid.
- To run the third check too, read the transaction and call `Transaction.fromHexBEEF(beefHex).verify(new WhatsOnChain('test'))`. It returns `true` when every check passes.
- `WhatsOnChain` is a chain tracker backed by the WhatsOnChain service. Any object with `isValidRootForHeight` and `currentHeight` methods works in its place, for example one backed by your own header store.

<Callout type="note">
  A chain tracker belongs to one network. `new WhatsOnChain()` defaults to Mainnet, so a testnet BEEF checked with it fails. Pass `'test'` on testnet and `'main'` on Mainnet.
</Callout>

### Make a BEEF

To make a BEEF from a transaction that is signed, has its inputs' source transactions set, and has a `merklePath` on the oldest ancestors:

```typescript
import { Transaction, Utils } from '@bsv/sdk'

// replace with a testnet BEEF as hex. In your own app, tx is a signed
// transaction with sourceTransaction on each input
const tx = Transaction.fromHexBEEF('BEEF_HEX')

const beefHex = tx.toHexBEEF()
const atomicBeef = tx.toAtomicBEEF()

console.log(beefHex.slice(0, 8))
console.log(Utils.toHex(atomicBeef.slice(0, 4)))
```

It prints the start of each form:

```text
0100beef
01010101
```

- `toHexBEEF` returns a V1 BEEF as hex, and `toAtomicBEEF` returns an Atomic BEEF as an array of bytes, with `tx` as the subject transaction.
- A transaction that you read with `Transaction.fromAtomicBEEF`, `Transaction.fromHexBEEF` or `Transaction.fromBEEF` already has its ancestors attached. `toHexBEEF` rebuilds a V1 BEEF from them, so a V1 input comes back unchanged, while an Atomic or V2 input comes back as V1, without the Atomic prefix and subject transaction ID. Use `toAtomicBEEF` when the receiver expects Atomic BEEF.
- A `new Beef()` that you fill by hand is V2 by default. Pass `BEEF_V1` to the constructor when the receiver expects V1.
